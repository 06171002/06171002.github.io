## 개요

여러 서비스(테넌트)가 OpenAI · Anthropic 모델을 한 입구로 쓰는 LLM 게이트웨이에서, 테넌트들이 **공급자 계정 하나를 함께 써도 남의 파일 · 벡터 스토어 · 컨테이너에 닿지 못하게** 한 설계다. 공급자는 키만 있으면 계정 안의 어떤 자료든 ID로 내준다. 그래서 게이트웨이가 **주인 장부**를 두고, 요청 본문 어디에 있든 자료 ID의 주인을 확인한다. 답에 처음 나온 ID는 **클라이언트가 받기 전에** 주인을 적고, 공급자가 스스로 하지 않는 정리는 게이트웨이가 맡는다.

<div class="table-wrap">

| **주인 장부**     | **본문 전체 확인** | **같은 404**  | **넘기기 전 기록** | **정리는 게이트웨이가**   |
| ------------- | ------------ | ----------- | ------------ | ---------------- |
| 게이트웨이로 만든 자료만 | 메타데이터만 제외    | 남의 것 = 없는 것 | 스트림은 이벤트 전에  | 스토어 빼기 · 만료 · 삭제 |

</div>

## 왜 필요했나 (Problem)

공급자에게 테넌트는 보이지 않는다. 모든 테넌트가 계정 하나를 같이 쓰면 공급자 눈에는 **모든 요청의 주인이 같다**. 테넌트 사이의 경계는 게이트웨이만 지킬 수 있다.

<aside class="callout tone-scenario" data-icon="🎯">

**시나리오 1 — 도구 결과 안에 넣은 남의 파일 ID**\
테넌트 B가 A의 파일 ID를 알게 됐다. 함수 도구를 부른 것처럼 꾸민 **도구 결과 안에** 그 ID를 넣어 보내면, 공급자는 키만 보고 파일을 내주고 모델은 A의 파일을 읽는다.\
정해진 칸만 보던 처음 구현에서는 이 요청이 그대로 공급자로 갈 수 있었다 → **독립 리뷰(코드를 읽기만 하는 별도 AI 리뷰어)가 '높음'으로 찾은 구멍**

</aside>

<aside class="callout tone-scenario" data-icon="🔁">

**시나리오 2 — 방금 받은 컨테이너 ID가 404**\
코드 실행이 새 컨테이너를 만들면 그 ID는 답(스트림이면 중간 이벤트)에 처음 나온다. 클라이언트가 그 ID로 곧바로 다음 요청을 보냈는데 게이트웨이가 아직 주인을 적지 않았다면 **자기 컨테이너가 404**가 된다.\
거꾸로 주인을 적지 못한 ID가 나가면 **누구도 쓰지도 지우지도 못하는 컨테이너**가 남는다.

</aside>

<aside class="callout tone-scenario" data-icon="🗑️">

**시나리오 3 — 지운 파일이 벡터 스토어에 남는다**\
공급자 문서는 파일을 지우면 벡터 스토어에서도 빠진다고 했다. 실제 확인에서는 **30초 뒤에도 스토어 목록에 남아 있었고 저장량도 그대로**였다. 스토어에 남은 파일은 그대로 검색 대상이고, 저장량만큼 요금이 붙는다.\
게다가 게이트웨이 장부에서는 이미 지운 파일이라, 테넌트가 스토어에서 뺄 길도 없었다.

</aside>

<aside class="callout tone-scenario" data-icon="💸">

**시나리오 4 — 응답에 나오지 않는 컨테이너 시간**\
OpenAI 컨테이너 값은 **살아 있는 시간 × 메모리**로 매겨지는데, 응답의 사용량에는 그 시간이 없다. 같은 컨테이너를 이어 쓰는 대화를 요청마다 새로 세면 몇 배로 부풀고, 세지 않으면 예산이 그 값을 놓친다.

</aside>

이 넷을 **주인 장부 + 본문 전체 확인 + 넘기기 전 기록 + 게이트웨이가 맡는 정리**로 풀었다.

## 핵심 설계 결정

### 1. 주인 장부 — 게이트웨이로 만든 자료만 적는다

<aside class="callout tone-blue" data-icon="📒">

파일 · 벡터 스토어 · 컨테이너 · 코드 실행이 만든 파일은 **게이트웨이를 거쳐 생길 때** 장부에 적힌다 — 만든 테넌트와 키, 만든 시각, 만료, 지운 시각.

- 게이트웨이를 거치지 않고 만든 자료는 장부에 없으므로 **ID를 알아도 쓸 수 없다**
- 장부에는 내용이 없다 — ID · 이름 · 크기 · 시각 같은 꼬리표만 둔다

</aside>

### 2. 본문 전체에서 찾고, 남의 것과 없는 것은 같은 404

<aside class="callout tone-orange" data-icon="🔎">

공급자가 ID로 읽지 않는 메타데이터 칸만 빼고, **모든 칸을 모든 깊이까지** 훑어 파일 · 벡터 스토어 · 컨테이너 ID를 모은다 — 메시지 첨부, 도구 결과, 화면 캡처, 지난 검색 결과, 인용, 도구 지정까지.

- 장부에 없으면 남의 것이든 없는 것이든 **같은 404**로 답하고 공급자에 보내지 않는다 — **있는지조차 알리지 않기 위해서**다
- 404에는 그 ID가 있던 칸을 적어, 클라이언트가 어디를 고칠지 알게 한다
- Anthropic 쪽은 블록 종류로 자리를 나눠, 알려진 자리 밖에 든 파일 ID는 400으로 거절한다
- 숨기는 것은 **남의 것뿐**이다 — 대화를 이을 컨테이너로 같은 테넌트가 가진 다른 공급자의 컨테이너를 보내면 400으로 알린다. 모델을 바꾼 탓임을 알게 하려는 것이다

</aside>

```text
# 요청 본문의 자료 ID 확인
for 칸 in 본문의 모든 칸 (메타데이터 제외):
    for 자료 ID in 그 칸의 모든 깊이:
        if 모델이 읽는 자리: 살아 있는 이 테넌트의 것이어야 한다
        else 지난 답 자리: 이 테넌트가 만든 적 있으면 된다
하나라도 어긋나면 → 404 (남의 것 · 없는 것 같은 답, 공급자에 안 보냄)
```

### 3. 지난 답 속 ID — 만든 적 있으면 통과

<aside class="callout tone-blue" data-icon="🧾">

대화를 공급자에 보관하지 않으므로, 클라이언트는 **지난 답을 매번 되돌려 보낸다**. 그 안의 인용 · 검색 결과 · 지난 코드 실행 기록에도 ID가 있다.

- 이것까지 살아 있어야 한다고 하면 파일을 지운 뒤 **그 파일을 인용한 대화가 막힌다** — 독립 리뷰가 찾은 문제다. 마지막 사용 20분 뒤 끝나는 컨테이너도 같다
- 그래서 **지난 답 자리는 그 테넌트가 만든 적 있으면 통과**로 정했다 — 지웠거나 끝났어도 된다
- 같은 ID가 **모델이 읽는 자리에도 있으면 살아 있어야** 한다 — 지운 파일을 다시 읽히는 길은 막힌다

</aside>

### 4. 새 ID는 공급자가 두는 자리에서만 읽고, 넘기기 전에 적는다

<aside class="callout tone-orange" data-icon="✍️">

답에서 새 컨테이너 · 만든 파일을 찾을 때는 **공급자가 ID를 두는 자리만** 읽는다 — 코드가 돈 기록, 셸이 쓴 환경, 만든 파일의 인용, Anthropic 답의 컨테이너 칸과 코드 실행 결과.

- 처음에는 스트림에서 인용 이벤트가 메시지 끝보다 먼저 와도 놓치지 않으려고 **답의 모든 깊이**를 읽었다. 독립 리뷰가 그 틈을 찾았다 — 공급자는 요청의 메타데이터를 답에 되돌려 주고, 파일 검색 결과에는 테넌트가 적은 속성이 실린다. 거기에 코드 실행 기록 모양으로 남의 컨테이너 ID를 심으면 **그 컨테이너가 내 것으로 적혔다**
- 새 컨테이너는 그 요청에 컨테이너를 만드는 도구가 있었을 때만 그 테넌트 것으로 적는다. 다른 테넌트의 ID가 답에 나오면 적지 않고 오류 로그를 남긴다
- 적는 때는 **클라이언트가 ID를 받기 전**, 스트림이면 **그 ID가 든 이벤트를 넘기기 전**이다. 적지 못하면 오류 이벤트로 스트림을 끝내 ID를 내보내지 않는다

</aside>

```text
# 스트림 중계 — 새 ID는 넘기기 전에 장부에 적는다
for 이벤트 in 공급자 스트림:
    새 ID = 공급자가 두는 자리의 ID − 이미 적은 ID
    if 새 ID가 있다:
        장부에 기록 (테넌트, 새 ID)
        실패하면 → 오류 이벤트를 보내고 끝낸다  # ID는 나가지 않는다
    클라이언트에 이벤트 전달
```

### 5. 목록은 장부로 답한다

<aside class="callout tone-blue" data-icon="📋">

파일 · 벡터 스토어 · 컨테이너 목록에 **무엇을 넣을지는 장부가 정한다**. 공급자에게 목록을 묻지 않는다.

- 공급자 목록은 계정 단위라 **남의 자료가 섞일 수 있다**
- 컨테이너는 **읽기만 해도 수명이 늘어** 값이 붙는다 — 그래서 컨테이너 목록은 공급자를 아예 부르지 않고 장부로 채운다

</aside>

### 6. 응답에 없는 컨테이너 시간 — '센 끝'으로 많게 센다

<aside class="callout tone-orange" data-icon="⏱️">

OpenAI 컨테이너는 **마지막 사용 뒤 20분이 지나면 끝나고**, 값은 20분마다 메모리에 따라 매겨진다(공개 가격표, 1GB면 $0.03). 응답에는 그 시간이 없다.

- 컨테이너마다 <strong>'센 끝'</strong>(이미 기록과 예산에 넣은 시간의 끝)을 장부에 둔다
- 쓸 때마다 '끝난 시각 + 20분'까지 모자란 시간을 **20분 칸으로 올려** 더 센다
- 같은 컨테이너를 동시에 쓴 두 요청이 같은 칸을 두 번 세지 않도록, 정산 트랜잭션에서 **컨테이너 줄을 예산보다 먼저 잠근다**
- **일부러 많게 센다** — 칸 올림, 시작은 요청 시작, 자동 도구를 주고 부르지 않아도 컨테이너 하나, 일찍 지워도 돌려주지 않음

</aside>

<div class="table-wrap">

| **시각**       | <strong>일 (1GB 컨테이너 하나)</strong> | **살 수 있는 끝** | **센 끝**       | **더 센 칸** | **값** |
| ------------ | -------------------------------- | ------------ | ------------- | --------- | ----- |
| 10:00\~10:01 | 첫 요청 — 자동 코드 실행이 새 컨테이너를 만든다     | 10:21        | 10:00 → 10:40 | 2         | $0.06 |
| 10:05\~10:06 | 같은 대화를 이어 쓴다                     | 10:26        | 10:40         | 0         | $0    |
| 10:12        | 만든 파일을 내려받는다                     | 10:32        | 10:40         | 0         | $0    |
| 10:30\~10:31 | 같은 컨테이너를 다시 쓴다                   | 10:51        | 10:40 → 11:00 | 1         | $0.03 |

</div>

<aside class="callout tone-green" data-icon="✅">

<strong>장부 합계 $0.09.</strong> 이 컨테이너는 10:51쯤 끝나 약 51분을 산다. 공급자가 20분 세션으로 세면 3세션 $0.09, 가격표 각주대로 분 단위로 세면 약 $0.077이다 — 장부는 **많게 세는 쪽**을 골랐다.

</aside>

### 7. 공급자가 하지 않는 정리는 게이트웨이가 맡는다

<aside class="callout tone-green" data-icon="🧹">

- **파일을 지울 때** — 그 테넌트의 벡터 스토어마다 먼저 빼고, 하나라도 실패하면 **지우기도 실패로 답해** 다시 시도할 수 있게 둔다(아래 「실측이 바꾼 것」)
- **정해 둔 만료가 지난 파일** — 매일 실행이 스토어에서 뺀 뒤 만료 시각으로 지운 것으로 적는다. 빼지 못하면 다음 실행으로 넘기고, 그동안에도 쓰지 못한다
- <strong>코드 실행이 만든 파일(Anthropic)</strong> — 공급자가 스스로 지우지 않으므로, 정해 둔 날수가 지나면 매일 실행이 지운다
- <strong>끝난 컨테이너(OpenAI)</strong> — 공급자에 묻지 않는다(읽으면 수명이 늘어난다). 센 끝에서 1시간이 지나면 센 끝 시각으로 끝난 것으로 적는다. 1시간은 늦게 오는 정산과 엇갈리지 않게 둔 틈이다
- **테넌트 단위 삭제** — 관리자가 명령 하나로 한 테넌트의 OpenAI 파일 · 벡터 스토어 · 컨테이너와 Anthropic 파일을 공급자에서 지우고, 감사 기록을 남긴다

</aside>

> 스토어 안 항목에서 404가 나면 스토어를 한 번 더 읽어 본 뒤에만 스토어를 지운 것으로 본다. 사라진 파일 하나를 넣으려다 **살아 있는 스토어를 지운 것으로 적던 결함**을 독립 리뷰가 찾았기 때문이다.

## 설계가 만든 결과 (Result)

<aside class="callout tone-blue" data-icon="📊">

이 설계의 핵심 주장은 둘이다 — <strong>① 남의 ID가 든 요청은 공급자에 가지 않는다 ② 새 ID는 주인을 적은 뒤에만 클라이언트에 간다.</strong> 가짜 공급자를 둔 통합 테스트로 불변식을 고정하고, 실제 공급자로 로컬에서 확인했다.

</aside>

### 테스트로 고정한 불변식

<div class="table-wrap">

| **불변식**                                                                          | **확인 방식**                                |
| -------------------------------------------------------------------------------- | ---------------------------------------- |
| **도구 결과 · 화면 캡처에 넣은 남의 파일 ID**, 게이트웨이 밖에서 만든 파일 ID → 404                         | 독립 리뷰가 찾은 구멍 재현 · 가짜 공급자 호출 **0건**       |
| 남의 컨테이너를 도구 정의 · 지난 기록 · 컨테이너 입구 어디로 가리켜도 404                                    | 요청 3가지 꼴 · 입구 작업 5가지 · 공급자 호출 수 그대로      |
| **되돌아온 메타데이터 · 검색 결과 속성에 심은 컨테이너 ID**는 장부에 적히지 않는다                               | 독립 리뷰가 찾은 구멍 재현 · 단위 · 통합(일반 답과 스트림)     |
| 지운 파일을 인용한 지난 답은 통과, 남의 파일 인용은 404, 지운 파일을 다시 읽히면 404                            | 지난 답 규칙                                  |
| **스트림에서 새 컨테이너 ID가 보인 순간** 그 ID로 보낸 다른 요청 → 200                                  | 같은 새 컨테이너를 쓴 두 요청의 칸 합 **2** (두 번 세지 않음) |
| Anthropic 코드 실행 — 만든 파일 · 컨테이너가 보인 이벤트 직후 스트림을 붙잡아 둔 채 조회 → 200                  | 이벤트 3종류                                  |
| 장부 기록이 실패하면 스트림은 오류 이벤트로 끝나고 그 ID는 나가지 않는다                                       | 기록 실패 주입                                 |
| 스토어 하나가 고장 나면 파일 지우기가 실패하고 파일이 남는다 → 다시 지우면 모든 스토어에서 빠진다                         | 남은 파일은 테넌트가 뺄 수 있고, 남의 파일은 404           |
| 컨테이너 목록은 장부에서만 나온다                                                               | 공급자에 목록을 묻는 호출 **0건**                    |
| 컨테이너 시간 — 정확히 20분이면 1칸, 20분 1초면 2칸 · 새 컨테이너 2칸($0.06) → 5분 뒤 이어 쓰기 0칸 → 30분 뒤 1칸 | 단위 · 통합                                  |
| 끝난 컨테이너 표시 — 센 끝에서 59분 뒤엔 그대로, 60분 뒤엔 끝남                                         | 끝난 시각 = 센 끝                              |

</div>

<aside class="callout tone-green" data-icon="✅">

**독립 리뷰가 찾은 두 구멍을 테스트로 재현해 고정했다** — 도구 결과 속 남의 파일 ID, 되돌아온 메타데이터에 심은 컨테이너 ID. 그리고 **ID가 보인 순간 다른 요청에 써도 200**이라는 순서 보장을 스트림 테스트로 고정했다.

</aside>

## 실측이 바꾼 것

### 1. 지운 파일이 벡터 스토어에 남았다 (2026-11-02)

<aside class="callout tone-red" data-icon="🔍">

<strong>문서와 실제가 달랐다.</strong> 공급자 문서는 파일을 지우면 모든 벡터 스토어에서도 조금 뒤 빠진다고 했다. 실제로는 지운 지 **30초 뒤에도 스토어 목록에 남아 있었고 저장량도 그대로**였다.\
게이트웨이 장부에서는 이미 지운 파일이라 **테넌트가 스토어에서 뺄 수도 없었다**.

</aside>

<aside class="callout tone-green" data-icon="✅">

<strong>지우는 순서를 바꿨다.</strong> 파일을 지울 때 그 테넌트의 벡터 스토어마다 먼저 빼고, 하나라도 실패하면 지우기 자체를 실패로 답한다. 스토어에서 빼기는 이미 지운 파일도 받는다. 만료된 파일과 공급자 쪽에서 사라진 파일도 같은 방식으로 뺀다.\
테스트의 가짜 공급자도 **실제처럼 지운 파일을 스토어에 남기도록** 바꿔, 테스트가 문서가 아니라 관찰한 동작을 따르게 했다.

</aside>

### 2. 만료된 컨테이너는 ID 없는 400으로 왔다 (2026-11-05)

<aside class="callout tone-red" data-icon="🔍">

21분 넘게 쓰지 않은 OpenAI 컨테이너로 대화를 이으니, 공급자가 **컨테이너 ID 없이 '만료됐다'는 400**을 주었고 그대로 클라이언트에 나갔다. 그 컨테이너의 파일을 내려받으면 404였는데도 **컨테이너 시간 $0.03을 셌다**. 같은 컨테이너를 읽으면 200에 상태 '만료'로 답했다.

</aside>

<aside class="callout tone-green" data-icon="✅">

- 그 400을 **남의 것 · 없는 것과 같은 404**로 바꾼다
- 그 400에는 컨테이너 ID가 없으므로 **요청이 가리킨 컨테이너가 하나일 때만** 그 컨테이너를 끝난 것으로 적는다
- 읽기에 '만료'로 답한 컨테이너도 끝난 것으로 보고 404로 답하며, **시간 값을 세지 않는다**

</aside>
