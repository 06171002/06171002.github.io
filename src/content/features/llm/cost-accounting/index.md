## 개요

사내 서비스(테넌트)들은 이 게이트웨이를 거쳐 유료 LLM을 쓰고, 테넌트마다 **예산 한도**가 있다. 게이트웨이는 요청마다 **기록한 비용**으로 예산을 깎는다. 그래서 기록에서 빠진 요금은 예산에서도 빠진다.\
이 기능은 유료 요금을 **빠짐없이 세는 규칙**이다. 카드 결제의 가승인처럼, 요청 전에 그 요청이 낼 수 있는 <strong>가장 큰 금액을 먼저 잡아 두고(예약)</strong>, 끝나면 공급자가 알려 준 <strong>실제 사용량으로 맞춘다(정산)</strong>. 요금을 셀 수 없는 기능은 아예 보내지 않는다.

<div class="table-wrap">

| **셀 수 없으면 막는다**            | **먼저 크게 잡는다**          | **끝나면 실제로 맞춘다**                      | **재 보고 고쳤다**                 |
| -------------------------- | ---------------------- | ------------------------------------ | ---------------------------- |
| 요금을 계산할 수 없는 기능은 보내기 전에 거절 | 요청 전에 낼 수 있는 최대 금액을 예약 | 공급자가 알려 준 사용량으로 정산 · 못 받으면 예약 금액 그대로 | 실제 공급자로 4번 재서 예약 식과 셈 규칙을 고침 |

</div>

---

## 왜 필요했나 (Problem)

코드를 읽기만 하는 별도 AI 리뷰어(독립 리뷰)가, 토큰만 세는 기록으로는 **예산에 잡히지 않는 비용**이 있다는 것을 찾았다.

<aside class="callout tone-scenario" data-icon="🎯">

**시나리오 1 — 답을 받기 전에 끊긴 요청이 0원으로 남는다**\
유료 요청이 답을 받기 전에 시간 초과로 끝나면, 게이트웨이는 사용량을 받지 못해 **0원**으로 적었다. 하지만 공급자는 이미 처리하고 청구했을 수 있다.\
→ **예산이 실제로 쓴 돈을 모른다**

</aside>

<aside class="callout tone-scenario" data-icon="🧾">

**시나리오 2 — 토큰 말고 따로 붙는 요금**

- 웹 검색은 **한 번 부를 때마다** 값이 붙는다
- 코드 실행은 **실행 시간**으로 값이 붙는데, 답에는 시간이 없다

→ 토큰만 세면 이 요금이 **예산 밖으로 샌다**

</aside>

<aside class="callout tone-scenario" data-icon="🔁">

**시나리오 3 — 검색 한 번에 입력이 두 배가 넘는다**\
웹 검색 같은 도구를 주면 모델은 공급자 안에서 **여러 번 실행**된다 — 검색하기 전에 한 번, 검색 결과를 받고 한 번. 실제로 재 보니 **실행할 때마다 프롬프트 전체를 다시 읽었다**.\
긴 프롬프트에 검색 한 번이면 입력이 **34,267 → 74,907토큰**이었는데(Claude Haiku), 예약은 프롬프트를 한 번만 세어 **약 41K**였다.\
→ 요청 전에 잡은 입력이 **실제의 절반 남짓**이었다

</aside>

## 한눈에 보는 흐름

검색을 한 번 하면 모델은 **두 번** 실행되고, 그때마다 프롬프트를 다시 읽는다.

> 정산은 처음부터 공급자가 알려 준 사용량으로 했다. 바뀐 것은 요청 전에 잡는 **예약**이다.

</div>

## 핵심 설계 결정

### 1. 셀 수 없으면 보내지 않는다

<aside class="callout tone-orange" data-icon="🚧">

도구와 옵션은 **게이트웨이가 요금을 셀 수 있게 만든 것부터** 열었다. 나머지는 공급자에 보내기 전에 **400**으로 거절하고, 대신 무엇을 쓰면 되는지 알린다.

- 예: 가격이 공개되지 않은 기능, 그림 크기 · 품질 '자동'처럼 결과를 봐야 값이 정해지는 옵션
- 그래도 요청에 없던 유료 도구 호출이 답에 나오면 요금표에서 **가장 비싼 값**으로 센다

</aside>

### 2. 예약은 크게, 정산은 실제로

<aside class="callout tone-orange" data-icon="💰">

예약은 그 요청이 낼 수 있는 **가장 큰 금액**이다 — 출력은 상한 끝까지, 입력은 더 비싼 캐시 쓰기 단가로(긴 프롬프트면 요청 전체를 긴 단가로), 도구는 쓸 수 있는 최대 횟수만큼 잡는다.

</aside>

<aside class="callout tone-blue" data-icon="📒">

요청이 끝나면 **어떻게 끝났는지**에 따라 기록한다.

- 공급자가 사용량을 알려 줌 → **사용량 × 단가 + 도구 요금**
- 보낸 뒤 사용량 없이 끝남(시간 초과 · 끊긴 연결) → **예약한 금액 그대로** — 공급자가 이미 처리했을 수 있다
- 공급자에 보내지도 못함 → 0원
- 답에 없는 코드 실행 시간 → 요청 시간 + 5분을 5분 단위로 올려 시간당 $0.05 (5분 안에 끝나면 $0.0083)

</aside>

### 3. 도구가 든 요청은 실행 횟수만큼 다시 센다

<aside class="callout tone-blue" data-icon="🔁">

웹 검색 · 코드 실행 같은 도구가 든 요청은 공급자 안에서 모델이 여러 번 실행되고, **실행할 때마다 프롬프트와 도구 정의(공급자가 붙이는 도구 설명)를 다시 읽는다**. 그래서 예약도 그렇게 센다.\
**입력 예약 = 실행 횟수 × (프롬프트 + 도구 정의) + 앞에서 나온 결과**

- 실행 횟수 = 웹 도구를 쓸 수 있는 횟수의 합 + 1 (검색 1번이면 2회). 코드 실행은 횟수를 정할 수 없어 공급자 문서의 반복 한도(요청마다 10회)로 잡는다
- 도구 정의의 크기는 재서 넣었다 — 웹 검색 2,816 · 웹 가져오기 1,046토큰
- 결과는 나온 뒤의 실행마다 다시 읽히므로, 큰 결과가 먼저 나오는 **가장 나쁜 경우**로 잡는다
- GPT 계열은 재 보니 프롬프트를 요청당 한 번만 읽어 이 식을 쓰지 않는다

</aside>

## 설계가 만든 결과 (Result)

<aside class="callout tone-blue" data-icon="📊">

핵심 주장은 둘이다. <strong>예약은 공급자가 실제로 쓴 양을 덮고, 기록은 공급자가 알려 준 사용량과 맞는다.</strong>\
앞의 것은 실측값을 넣은 단위 테스트로, 뒤의 것은 실제 공급자 비용 대조로 확인했다.

</aside>

### 테스트로 고정한 것

가짜 공급자와 로컬 DB로 돈다. 서버 도구를 연 단계에서 전체 896개가 통과했다.

<div class="table-wrap">

| **확인한 것**                                          | **결과**                                       |
| -------------------------------------------------- | -------------------------------------------- |
| **측정한 요청의 예약** — 프롬프트 31,451토큰(도구 정의 제외), 검색 최대 1번 | 새 식 **77,154 ≥ 실제 74,907** · 옛 식 39,761은 모자람 |
| 예산 한도 $0.10에 검색 최대 10번인 요청 (Claude 계열)             | **429**로 막고 공급자를 부르지 않음 · 최대 1번이면 통과         |
| 답 전에 시간 초과한 유료 요청                                  | **예약 금액 그대로**(약 $0.041) 기록                   |
| 셀 수 없는 도구 · 옵션                                     | 모두 **400** · 공급자 호출 0                        |

### 실측 (로컬)

<strong>실제 확인은 내가 비용을 승인하고 키를 넣어 두면, AI 코딩 에이전트가 로컬 게이트웨이에서 일회용 테넌트로 요청을 보내는 방식으로 했다.</strong>

## 실측이 바꾼 것

계획에 **중단 조건**을 미리 적어 두었다 — 기록이 공급자와 10% 넘게 다르거나, 검색한 요청의 입력이 실행마다 프롬프트를 다시 센 만큼 크면 멈추고 다시 정한다. <strong>두 조건이 실제로 걸렸다.</strong>

<aside class="callout tone-red" data-icon="🔁">

<strong>① 실행마다 다시 읽는다 → 예약 식을 바꿨다 (2026-11-04)</strong>\
검색 한 번에 입력이 34,267 → 74,907토큰이었다. 예약 약 41K로는 모자랐다.\
실행 횟수만큼 다시 세는 식으로 바꾸자, 측정한 크기로 계산한 예약이 **77,154토큰으로 실제를 덮었다**(옛 식 39,761). 이 측정을 단위 테스트로 고정했다.

</aside>

<aside class="callout tone-red" data-icon="🧮">

<strong>② 많게 세려던 규칙이 과다 기록이었다 → 공급자가 센 횟수로 (2026-11-04)</strong>\
문서가 일부 검색 동작의 요금을 밝히지 않아, 답에 나온 검색 항목을 하나씩 셌다. 대조해 보니 GPT 계열은 쪽 열기 항목까지 검색으로 셌고(공급자 1번 · 기록 2번), Claude 계열은 실제로 돌지 않은 검색까지 셌다.\
→ 검색은 **공급자가 답에 적은 횟수**로 센다.

</aside>
