## 개요

테넌트별 LLM 비용을 막는 것은 **게이트웨이 예산**이고, 예산은 게이트웨이가 **기록한 비용**으로 센다. 그래서 기록에서 빠진 요금은 예산에서도 빠진다.\
이 기능은 유료 요청의 요금을 **빠짐없이 세는 규칙**이다. 요금을 셀 수 없는 기능은 **보내기 전에 막고**, 셀 수 있는 것은 요청 전에 **낼 수 있는 가장 큰 값으로 예약**하며, 끝나면 **공급자가 알려 준 사용량으로 정산**한다. 실제 공급자로 잰 값이 가정과 다를 때마다 예약 식과 셈 규칙을 고쳤다.

<div class="table-wrap">

| **셀 수 없으면 400**               | **못 받은 사용량 = 최대**             | **바퀴 모형 예약**               | **공급자가 센 횟수**         | **실측 4번**                |
| ----------------------------- | ----------------------------- | -------------------------- | --------------------- | ------------------------ |
| 값이 공개되지 않은 입구 · 옵션은 보내기 전에 거절 | 보낸 뒤 사용량 없이 끝난 유료 요청은 예약 금액으로 | 바퀴 수 × (프롬프트 + 도구 정의) + 결과 | 검색 요금은 공급자가 답에 적은 횟수로 | 2026-11-02 \~ 11-05 · 로컬 |

</div>

## 왜 필요했나 (Problem)

독립 리뷰(코드를 읽기만 하는 별도 AI 리뷰어)가 달러 예산에 잡히지 않는 비용을 찾았다 — **도구 요금, 긴 프롬프트의 높은 단가, 시간 초과로 끝난 요청, 끊긴 요청의 보이지 않는 추론 토큰**이다. 도구를 열수록 이런 틈은 늘어난다.

<aside class="callout tone-scenario" data-icon="🎯">

**시나리오 1 — 답 전에 끝난 유료 요청이 0원으로 남는다**\
스트림이 아닌 유료 요청이 답을 받기 전에 시간 초과로 끝났다. 게이트웨이는 토큰 수를 받지 못해 **비용 0**으로 기록했다.\
그런데 공급자는 이미 요청을 받아 처리하고 청구했을 수 있다. 화면에 나오지 않는 추론 토큰은 받은 글자로 어림할 수도 없다.\
→ **예산이 쓴 돈을 모른 채 다음 요청을 들인다**

</aside>

<aside class="callout tone-scenario" data-icon="🧾">

**시나리오 2 — 답에 값이 적히지 않는 요금**

- 웹 검색은 **호출마다 값**이 붙고, 검색 결과는 다시 **입력 토큰**으로 청구된다
- 코드 실행은 **실행 시간**으로 청구되는데, 답에는 시간이 없다
- 그림의 크기 · 품질을 '자동'으로 두면 값이 **그려진 그림에 따라** 달라진다

→ 토큰만 세는 기록으로는 이 요금들이 **예산 밖으로 샌다**

</aside>

<aside class="callout tone-scenario" data-icon="🔁">

**시나리오 3 — 공급자 안에서 여러 바퀴 도는 서버 도구**\
서버 쪽 도구(웹 검색 · 웹 가져오기 · 코드 실행)는 공급자 안에서 여러 바퀴 돈다. 실제로 재 보니 <strong>바퀴마다 프롬프트 전체와 도구 정의를 다시 읽었다.</strong>\
긴 시스템 프롬프트에 웹 검색 도구를 준 요청은 검색하지 않으면 입력 **34,267토큰**, 검색 한 번이면 **74,907토큰**이었다(Claude Haiku). 예약은 프롬프트를 한 번만 세어 **약 41K**였다.\
→ 정산은 공급자 사용량이라 정확했지만, **요청 전 사전 확인이 실제에 한참 못 미쳤다**

</aside>

## 핵심 설계 결정

### 1. 셀 수 없으면 열지 않는다

<aside class="callout tone-orange" data-icon="🚧">

도구는 모두 열되, **게이트웨이가 요금을 셀 수 있게 만든 것부터 단계별로** 열기로 정했다. 그 밖의 것은 공급자에 보내기 전에 **400**으로 거절하고, 대신 무엇을 쓰면 되는지 알린다.

- 한 장이 몇 토큰인지 공개되지 않은 새 이미지 모델 · 입력 그림의 토큰을 셀 수 없는 이미지 편집
- 값이 그려진 그림에 따라 달라지는 크기 · 품질 '자동'
- 요금이 다른 옛 검색 도구 · 단가가 달라지는 빠른 모드
- 요금이 공개되지 않은 벡터 저장소 검색 입구
- 그 안의 도구와 설정을 게이트웨이가 볼 수 없는 저장된 프롬프트
- 어디서 돌고 얼마인지 밝혀지지 않은 '프로그램이 부르는 도구 호출'
- 막힌 도구의 지난 출력 항목을 입력으로 다시 넘겨 그 자원을 다시 쓰는 요청

</aside>

```text
# 보내기 전에 — 요청의 도구와 옵션, 지난 출력 항목 속 도구까지 하나씩 본다
for 도구 in 요청의 도구:
    if 도구 in 값을 셀 수 없는 것:         return 400   # 무엇을 쓰면 되는지 안내
    if 옵션의 값이 결과에 따라 달라진다:   return 400   # 예: 그림 크기 '자동'
    한 번의 값 = 요금표[도구]                 # 예약과 정산이 같은 요금표를 본다
```

<aside class="callout tone-gray" data-icon="🛡️">

**막아도 생길 경우의 안전장치**\
요청에 없던 요금 도구 호출이 답에 나오면 요금표에서 **가장 비싼 값**으로 센다. 서버 도구는 테넌트가 **쓰겠다고 표시한 것만** 열고, 표시가 없으면 403이다.

</aside>

### 2. 끝나는 모양마다 기록할 값을 정했다

<aside class="callout tone-blue" data-icon="📒">

요청이 어떻게 끝났는지에 따라 기록할 값을 나눴다.

- **공급자가 사용량을 알려 줌** → 사용량 × 단가 + 도구 요금. 캐시 읽기 · 쓰기는 각자의 단가로 센다
- **공급자가 스스로 실패를 알림** → 받은 만큼 어림
- **보낸 뒤 사용량 없이 끝남** — 시간 초과 · 보낸 뒤 끊긴 연결 · 클라이언트가 끊음 · 끊긴 스트림 → **예약한 최대 금액**
- **보내지 못함** — 연결이나 연결 자리를 얻지 못한 시간 초과, 자리를 기다리다 떠난 클라이언트 → 0
- **무료 모델** → 받은 글자로 어림해 토큰 예산에 넣는다

</aside>

```text
if 공급자 사용량이 있다:       비용 = 사용량 × 단가 + 도구 요금
elif 공급자가 실패를 알렸다:   비용 = 받은 만큼 어림
elif 공급자에 보내지 않았다:   비용 = 0
elif 유료 모델이다:            비용 = 예약한 최대 금액     # 처리 · 청구됐을 수 있다
else:                          토큰 = 받은 글자로 어림      # 무료 모델 — 토큰 예산에 든다
```

사용량을 못 받은 유료 요청을 예약 금액으로 적는 안은 2026-10-30에 골랐다. 공급자가 알린 실패를 받은 만큼으로 좁힌 것은 2026-11-02에 그대로 두기로 정했다.

### 3. 예약은 그 요청이 낼 수 있는 가장 큰 값

<aside class="callout tone-orange" data-icon="💰">

예약은 요청 전 사전 확인이면서, 사용량을 못 받은 요청의 기록값이다. 그래서 **그 요청이 낼 수 있는 가장 큰 값**으로 잡는다.

- 입력은 모두 **캐시 쓰기 단가**로 — 더 긴 캐시를 청하면 그 단가로
- 입력이 긴 프롬프트 선(GPT 계열은 27만 2천 토큰)을 넘으면 **요청 전체를 긴 단가**로 — 가격표가 넘는 부분에만 붙는지 밝히지 않아 많게 센다
- 도구는 **호출 상한 × 가장 비싼 한 번의 값**에, 결과로 읽을 입력(검색 한 번에 8,000토큰)을 더한다. 호출 상한이 없으면 5로 채우고, 서버 도구는 클라이언트가 사용 상한을 1\~10으로 꼭 적는다
- 코드 실행은 **시간 한도 끝까지**의 시간 값

</aside>

### 4. 바퀴 모형 — 서버 도구의 입력을 바퀴마다 다시 센다

<aside class="callout tone-blue" data-icon="🔁">

서버 도구가 든 요청의 입력은 **도구를 한 번 쓸 때마다 바퀴 하나, 큰 결과가 먼저 나오는 가장 나쁜 경우**로 잡는다.

- **바퀴 수** = 웹 도구 사용 상한의 합 + 1. 코드 실행에는 사용 상한이 없어, 코드가 돌면 서버 쪽 반복 한도(10바퀴)로 잡는다
- **프롬프트** = 글자 어림 + 첨부 + 도구를 줄 때 공급자가 더하는 안내 프롬프트(286토큰)
- **도구 정의** = 실측값 — 웹 검색 2,816 · 웹 가져오기 1,046 · 코드 실행 2,571 · 문서 만들기 기능 하나 477토큰
- **결과** = 검색 한 번 8,000 · 가져오기는 내용 상한의 1.5배 · 코드 실행 한 번 10,000토큰(5번으로 가정). i 번째로 큰 결과를 max(바퀴 수 − i, 1)번 센다

</aside>

```text
바퀴 수 = 웹 도구 사용 상한의 합 + 1
if 코드가 돈다: 바퀴 수 = max(바퀴 수, 10)            # 서버 쪽 반복 한도
결과들 = 쓰임마다의 결과 크기를 큰 것부터 늘어놓은 목록
입력 = 바퀴 수 × (프롬프트 + 도구 정의)
for i, 결과 in 결과들 (1부터):
    입력 += 결과 × max(바퀴 수 − i, 1)                  # 나온 뒤 바퀴마다 다시 읽힌다
```

검색 5번만이면 6바퀴이고 결과 몫만 8,000 × (5+4+3+2+1) = **120,000토큰**이다. 코드 실행만이면 10바퀴에 10,000 × (9+8+7+6+5) = **350,000토큰**이다. 같은 식을 요청을 그대로 넘기는 길, 변환하는 길, 공급자가 부르는 MCP 호출에 함께 쓴다.

### 5. 답에 없는 시간 요금은 요청 시간으로 센다

<aside class="callout tone-green" data-icon="⏱️">

코드 실행은 실행 시간으로 청구되지만 답에는 시간이 없다. 그래서 **요청이 걸린 시간 + 5분**을 5분 칸으로 올려 시간당 $0.05로 센다. 5분 안에 끝나면 2칸, <strong>$0.0083</strong>이다.

- 시간은 공급자에 **보낸 때부터** 잰다. 자리를 기다린 시간은 넣지 않는다
- 사용량을 못 받은 요청은 **시간 한도 끝까지** 쓴 것으로 본다
- 결과를 코드로 거르는 새 판 웹 도구가 든 요청은 공급자 가격표대로 시간 값이 없다

</aside>

<aside class="callout tone-blue" data-icon="📊">

## 실측이 바꾼 것

계획에 **중단 조건**을 미리 적어 두었다 — 기록한 비용이 공급자와 10% 넘게 다르거나, 여러 번 검색한 요청의 입력이 바퀴마다 프롬프트를 다시 센 만큼 크면 멈추고 다시 정한다. <strong>두 조건이 실제로 걸렸다.</strong>

<aside class="callout tone-red" data-icon="🔁">

<strong>① 바퀴마다 다시 읽는다 → 예약 식을 바꿨다 (2026-11-04)</strong>\
검색 한 번에 입력이 34,267 → 74,907토큰이었다. 예약 약 41K로는 사전 확인이 모자랐다. 같은 날 바퀴 모형 → 결과 누적 → 코드 실행 10바퀴 순서로 정했다.\
측정한 크기를 그대로 넣으면 새 식은 **77,154토큰으로 실제 74,907을 덮고**, 옛 식은 39,761이다. 이 측정을 단위 테스트로 고정했다.

</aside>

<aside class="callout tone-red" data-icon="📏">

**② 도구 정의는 가정보다 훨씬 컸다**\
계획은 도구를 줄 때 공급자가 더하는 안내 프롬프트(286토큰)만 셌다. 실측한 정의는 웹 검색 **2,816**(가정의 열 배 가까이) · 웹 가져오기 **1,046토큰**이었다.\
가져오기는 내용 상한 10,000토큰에 약 13.4K를 가져와, 결과를 상한의 1.5배로 잡는다.

</aside>

<aside class="callout tone-red" data-icon="🧮">

**③ 많게 세려던 규칙이 실제로는 과다 청구였다**\
문서가 쪽 열기 · 쪽 안 찾기의 요금을 밝히지 않아, 검색 항목 하나를 1번으로 세기로 했었다. 비용 대조에서 GPT 계열 +9.5%, Claude 계열 +12%가 나와 중단 조건에 걸렸다.\
원인은 둘이었다 — GPT 계열은 **쪽 열기 항목까지 검색으로** 셌고(공급자 1번 · 기록 2번), Claude 계열은 함수 호출과 함께 부른 검색이 **돌지 않았는데** 블록 수로 셌다.\
→ 검색은 **공급자가 답에 적은 횟수**로 세고, 항목 · 블록 수는 마지막 사용량 전에 끊긴 스트림에만 쓰도록 고쳤다.

</aside>

<aside class="callout tone-orange" data-icon="⚠️">

**④ 실패가 200으로 보이는 조합을 막았다**\
결과를 코드로 거르는 새 판 웹 도구를 코드 실행 없이 보내자, 공급자가 컨테이너를 만들지 않아 도구 호출이 실패했는데 요청은 **200**이었고 모델은 제 지식으로 답했다. 공급자 문서는 코드 실행 도구를 더하지 않아도 마련한다고 적고 있었다.\
→ 이 조합은 보내기 전에 400으로 거절하고, 코드 실행과 함께 보내거나 기본 판을 쓰라고 알린다.

</aside>

<aside class="callout tone-blue" data-icon="✅">

**⑤ 재 보고 바꾸지 않은 것**

- GPT 계열은 프롬프트를 요청당 한 번 읽어, 바퀴 모형을 걸지 않고 기존 식을 유지했다(2026-11-04 · 11-05)
- 검색 결과 토큰이 입력에 든다는 것을 확인하고, 검색 한 번의 예약 8,000토큰을 그대로 두었다
- 코드 실행의 예약은 정산보다 훨씬 컸다(예약 약 $1.39 · 정산 $0.06\~0.09). 바퀴 수와 결과를 최악으로 잡은 식이라 생기는 차이다. 그대로 두고 예산에 주는 영향을 사용 안내에 적기로 정했다(2026-11-05)

</aside>
