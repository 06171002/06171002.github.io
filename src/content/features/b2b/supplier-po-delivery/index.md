## 개요

공급사가 주문 시점에 자동 분리된 **발주(PO)를 받아 처리하는 순방향 워크플로우**를 담당. 발주 접수 → 출고(운송장) → 배송중 → 배송완료의 흐름을 **분할출고·합배송·엑셀 일괄처리**까지 받쳐 설계했다.

<div class="table-wrap">

| **PO-라인-배송 계층**      | **주문라인 1:1 분할출고**       | **합배송 자동전파** | **배송완료 단일화**   |
| -------------------- | ----------------------- | ------------ | -------------- |
| SKU로 합쳤다가 출고 때 다시 나눔 | 잔여 누적 차감으로 출고마다 주문라인 지정 | 번들키 공유 전파    | 수기 = 배치 공통 5단계 |

</div>

## 왜 이 설계가 필요했는가 (Problem)

<aside class="callout tone-scenario" data-icon="🎯">

**시나리오 1 — 분할출고 추적 불가**\
한 PO 라인은 같은 SKU를 주문한 **여러 주문라인을 N:1로 집계**하고, 동시에 **여러 운송장으로 분할 출고**(1:N)될 수 있다.\
그러면 "이 운송장이 어느 주문 건의 출고분인가?"를 추적할 수 없다\
→ **고객별 배송현황·부분정산 불가**.

</aside>

<aside class="callout tone-scenario" data-icon="📦">

<strong>시나리오 2 — 여러 박스를 한 운송장으로 (합배송)</strong>\
같은 수령지로 가는 여러 PO 배송을 한 박스로 묶어 보내는데, 작업자가 각 배송건마다 같은 운송장번호를 일일이 입력하면 오류·공수.\
→ **대표 1건에만 입력하면 묶음 전체에 자동 전파**되어야 한다.

</aside>

<aside class="callout tone-scenario" data-icon="📊">

**시나리오 3 — 수십\~수백 건 운송장 입력**\
공급사는 택배 프로그램으로 송장을 일괄 발급한다. 화면에서 한 건씩 입력하는 건 비현실적.\
→ **배송리스트 다운로드 → 송장 발급 → 엑셀 업로드 일괄 출고** 왕복 흐름이 필요하고, 다운로드↔업로드 사이 **식별자를 잃지 않는 키**가 있어야 한다.

</aside>

<aside class="callout tone-scenario" data-icon="🔀">

**시나리오 4 — 배송완료 처리의 중복**\
배송완료는 세 진입점에서 발생한다.

- **공급사 수기**
- **관리자 수기**
- **택배 추적 배치**

각자 입고검수 생성·상태 동기화를 중복 구현하면 **로직 드리프트** 위험\
→ **단일 진입점 필요**.

</aside>

## 테이블 설계 — PO 계층 + 배송 레코드

<aside class="callout tone-blue" data-icon="💡">

**계층 구조**: 주문라인(주문 단위) → PO(공급사 묶음) → PO라인(SKU 집계) → PO배송(개별 출고 1건).

- 주문은 SKU로 <strong>합쳐졌다가(PO라인)</strong> 출고 시점에 다시 <strong>주문라인 단위로 쪼개진다(PO배송)</strong>.
- 발주 엔티티는 공통 모듈로 단일화되어 공급사·관리자 앱이 공유.

</aside>

### 발주 배송 — 출고 레코드 핵심

<div class="table-wrap">

| **분류**      | **담는 것**              | **설계 의도**                                                   |
| ----------- | --------------------- | ----------------------------------------------------------- |
| 주문라인 1:1 매칭 | 주문라인 참조 (NULL 허용)     | 집계 PO라인이 잃은 "이 출고가 어느 주문라인을 채우는가"를 복원. 마이너스/레거시 PO는 NULL 허용 |
| 분할출고        | 출고 수량 · PO라인 참조(FK)   | 접수 시 유효수량만큼 출고 수량 1인 레코드로 나눔 → 출고 1건 = 1레코드                 |
| 합배송         | 번들키(묶음 식별) · 박스번호     | 여러 출고를 한 운송장으로. 같은 키 형제에 운송장 자동 전파                          |
| 배송상태        | 배송 상태 (준비→배송중→완료, 취소) | 출고건별 상태. 접수 시 '준비' 초기값                                      |
| 운송장         | 택배사 · 송장번호            | 택배 출고의 송장. 직배송은 송장 없이 상태만 전환                                |
| 일시          | 출고 시각 · 완료 시각         | 출고/완료 시각 (배치 추적 윈도우 기준)                                     |

</div>

### PO 라인 — 취소 3트랙 (귀책 분리)

<aside class="callout tone-gray" data-icon="⚖️">

**주문수량 = 고객사 귀책 취소 + 공급사 귀책 취소 + 출고 + 미출고** 수량 보존식을 유지.\
**고객사 귀책 취소 · 공급사 귀책 취소 · 미출고**를 각각 별도 누적해, 합치면 잃을 "누가 왜 취소했는가"를 보존(정산·책임 소재 직결).\
→ 누적합이 주문수량과 같아질 때만 라인을 취소·완료로 종결.

</aside>

## 핵심 설계 결정

### 1. 주문라인 1:1 분할출고 매칭 — 출고 할당기

<aside class="callout tone-orange" data-icon="🎯">

집계(N:1)로 잃어버린 "이 출고가 어느 주문라인의 출고분인가"를, **출고 레코드(출고 수량 1)가 주문라인을 1:1로 가리키게** 복원. 접수 시점에 유효수량만큼 개별 레코드를 만들면서 <strong>주문라인 순서(오름차순)</strong> 로 잔여를 누적 차감해 할당한다.

</aside>

```text
// 출고 할당 — 주문라인 잔여를 앞에서부터 순회하며 출고량만큼 차감
for (주문라인, 잔여) in 주문라인별 잔여(오름차순):
    if 잔여 ≥ 출고량:
        잔여 −= 출고량
        return 주문라인  // 이 출고 레코드가 매핑될 주문라인
return 없음  // 잔여 정보 없음(마이너스 PO·레거시) → best-effort
```

<aside class="callout tone-green" data-icon="✅">

동기화도 이 값 기준 — 주문라인 상태를 각 주문라인이 매핑된 PO라인 상태로 **1:1 미러링**. 단, **정방향 PO 한정** — 반품/교환 마이너스 PO·레거시 데이터는 매핑이 비어 있을 수 있어 best-effort.

</aside>

### 2. 합배송 운송장 자동 전파

<aside class="callout tone-blue" data-icon="📦">

사용자가 묶은 **번들키**를 공유하는 배송건들은, **대표 1건에 운송장을 입력하면 형제 레코드에 동일 운송장이 자동 확장** 적용된다. (수령지 동일성을 코드가 자동 판단하는 게 아니라, 사용자가 부여한 번들키 기준 전파.)

</aside>

```text
-- 대표 1건 운송장 입력 → 같은 번들키 형제에 동일 운송장 확장
SELECT 배송 ID FROM 발주 배송
 WHERE 번들키 = :번들키
   AND 배송 상태 = '준비' AND 삭제 아님
```

<aside class="callout tone-gray" data-icon="🛡️">

**묶음 무결성 방어**

- 합포장 설정은 레코드 재생성이 아닌 **번들키만 UPDATE**해 PK·FK 참조 안정성 유지
- 운송장 일괄 수정 시 묶음 일부 라인만 요청되면 예외(묶음 통째로만 처리)
- 운송장 발급된 박스는 '현재 최대 박스번호 + 1'로 채번해 번호 중복 방지

</aside>

### 3. 운송장 엑셀 일괄출고

<aside class="callout tone-blue" data-icon="📊">

**왕복 키 = 배송 레코드 PK**

- **다운로드** — '준비' 레코드를 만들며 PK를 엑셀 "관리번호"로 박아 내려보냄
- **업로드** — 거기서 배송 ID를 추출해 매칭
- **택배사** — 코드값·한글명 둘 다 허용해 정규화

</aside>

```text
// 업로드: 관리번호(A열)에서 배송 ID 추출 → 소유·상태·택배사 검증 → 일괄 출고
배송 ID = 관리번호 앞부분의 숫자 (정규식 ^(\d+))
// 검증: '준비'가 아니면 "이미 출고", 택배사가 이미 있으면 "이미 운송장 등록" → 중복 차단
```

<aside class="callout tone-green" data-icon="✅">

2-pass 후처리:\
① 존재·소유(공급사)·상태·중복 검증 + 택배사 유연입력 정규화\
② **합배송 형제 가상행 확장**(엑셀 1행 → N건 출고)\
엑셀 지수표기(3.17E+11)는 관리번호/운송장 컬럼을 TEXT 포맷으로 설정해 방지.

</aside>

### 4. PO 라인 부분취소 — 단가 내림차순 환불 최대화

<aside class="callout tone-purple" data-icon="💰">

집계 PO라인에서 N개 취소가 발생했을 때, **실결제 단가가 높은 주문라인부터 차감**한다 — 고객사가 환불받는 총액을 최대화하기 위함. 쿠폰/포인트는 '배분액 / 수량' 비례배분.

</aside>

```text
-- 후보 정렬: 단가(결제금액 / 수량) 내림차순 → 동일단가 FIFO
UPDATE 주문라인
   SET 공급사 취소수량 = 공급사 취소수량 + :취소수량
 WHERE … AND (고객사 취소 + 공급사 취소 + :취소수량) ≤ 주문수량  -- 경쟁 update 가드
-- 갱신 행 수가 0 이면 동시성 충돌 의심 예외 (낙관적 동시성 방어)
```

<aside class="callout tone-gray" data-icon="📝">

공급사 부분취소는 양수 PO라인 차감 + 취소 클레임(즉시 종결) 생성으로 처리(마이너스 PO 아님).

- **예산기업** — 예산 사용 내역에 음수 행
- **비예산** — 여신 직접 환원

**주의**: 비례배분 정수 잔차는 허용(라인 합계 보전 미적용).

</aside>

### 5. 직배송 안전망

<aside class="callout tone-orange" data-icon="🚫">

직배송은 운송장이 없으므로 택배 송장 기반 경로 전체에서 제외되고, 전용 도메인 메서드로 수기 "배송중" 전환. **엑셀출고·배송리스트·추적 배치 세 경로 모두에서 직배송을 다중 차단**하는 게 핵심(안전망).

</aside>

```text
직배송 시작():  // 운송장 없이 배송중 전환
    배송 상태 = 배송중
    출고 시각 = 지금
// 엑셀 출고: 직배송 라인이면 "직배송 상품은 운송장 입력 대상이 아닙니다" 예외
// 배송리스트 조회: 배송 유형이 직배송인 건 제외
// 배송 유형 변경은 '신규 발주' 라인만 허용 (접수 후엔 배송 레코드가 생겨 고정)
```

### 6. 배송완료 단일화 — 공통 완료 처리기

<aside class="callout tone-green" data-icon="🔀">

공급사 수기·관리자 수기·**택배추적 배치** 3개 진입점이 공통 모듈의 단일 컴포넌트를 호출. 배송완료 부수작업 5단계를 **트랜잭션 한 단위**로 묶어 경로가 달라도 동일하게 처리.

</aside>

```text
배송완료(라인 목록, 처리자):
  1) 발주 배송 → 배송완료
  2) PO라인 배송·라인 상태 → 배송완료
  3) 입고검수 생성 (구매사의 자동 입고 설정에 따라 검수완료/검수대기)
  4) PO라인 검수 상태 집계
  5) PO 헤더 + 주문 상태 동기화
// 입고수량 = 주문수량 − 취소 − 미출고 ≤ 0 이면 입고검수 생성·알림 skip
```

<aside class="callout tone-gray" data-icon="📦">

정방향 유형만 처리(교환 재배송·반품 수거 마이너스 PO는 클레임 서비스가 별도 처리). 반환값(생성된 라인 목록)이 비면 배치는 배송완료 알림을 보내지 않는다(멱등).

</aside>

### 7. 배송추적 배치

<aside class="callout tone-blue" data-icon="📡">

3-레이어 분리: **외부 배송추적 API 호출은 트랜잭션 밖에서** 건별로 하고, row 단위 부수작업만 짧은 트랜잭션으로 분리(수백 회 HTTP 동안 DB 커넥션 점유 회피).

- **완료 판정** — 응답의 **완료 플래그**
- **실패 격리** — 개별 row 실패는 catch로 격리해 전체 배치 보호

</aside>

**외부 API 쿼터 보호**

## 설계가 만든 결과 (Result)

<aside class="callout tone-blue" data-icon="📊">

「취소 3트랙(귀책 분리)」이 실제로 수량 보존식을 지키는지 **property 기반 테스트로 검증**했다.\
부분취소는 고객사·공급사 귀책이 섞여 여러 번 누적되므로, <strong>예시 몇 개로는 순서 조합을 덮을 수 없다.</strong>

</aside>

### 검증 결과

공통 모듈의 PO라인 엔티티 테스트 · **8/8 통과** (property 4종 · 총 32,000 케이스)

<div class="table-wrap">

| **불변식**                                                        | **케이스** |
| -------------------------------------------------------------- | ------- |
| 어떤 순서·분할로 취소해도 누적(고객사+공급사)이 주문수량을 넘지 않고, **초과요청은 필드를 바꾸지 않는다** | 10,000  |
| 누적이 **정확히** 주문수량과 같아질 때만 '발주 취소'로 전환된다                         | 10,000  |
| 미출고 포함 4항 합계가 주문수량을 넘지 못하고, 같으면 '배송 완료'로 종결된다                  | 10,000  |
| 미출고는 누적이 아니라 **덮어쓰기**다 (한 번에 확정하는 도메인 규칙)                      | 2,000   |

</div>

<aside class="callout tone-green" data-icon="✅">

검증 대상 항등식 — **주문수량 = 고객사 취소 + 공급사 취소 + 출고 + 미출고**\
이 식이 깨지면 <strong>정산 근거(누가 왜 취소했는가)와 라인 종결 판정이 동시에 틀어진다.</strong>

</aside>

### 거절 시 무변경을 명시적으로 잠갔다

<aside class="callout tone-orange" data-icon="🔒">

엔티티는 지역변수로 계산 → 검증 → 대입 순서라, 초과 요청 시 필드가 <strong>부분 적용되지 않는다.</strong>\
그런데 이건 **리팩터링으로 대입 순서만 바뀌어도 조용히 깨지는** 성질이라 회귀 테스트로 고정했다.\
→ 주문 10개에 고객사 7 취소 후 공급사 4를 시도하면, 공급사 취소수량이 3이 아니라 **0** 이어야 한다고 단언한다.

</aside>

### 랜덤 시퀀스가 성공·거절 경로를 함께 덮는다

거절 경로를 별도 테스트로 빼지 않고 **한 시퀀스 안에서 섞어** 검증한다. 랜덤 취소 시퀀스를 걸으며 각 단계마다 —

<div class="table-wrap">

| **조건**  | **기대**                |
| ------- | --------------------- |
| 잔여 ≥ 요청 | 성공 + 누적 증가            |
| 잔여 < 요청 | 인자 오류 예외 · **필드 무변경** |

</div>

→ 실제 운영에서 벌어지는 순서(부분취소가 여러 번 오다가 한계 초과)를 그대로 재현한다.

### 주문라인 1:1 분할출고 매칭 — 불변식 검증

<aside class="callout tone-green" data-icon="🎯">

이 카드의 핵심인 <strong>1번 결정(주문라인 1:1 매칭)</strong>을 불변식으로 잠갔다.\
공통 모듈의 출고 할당기 테스트 · **10/10 통과** (property 4종 · 랜덤 **32,000 케이스** + 경계 예시 6)

</aside>

<div class="table-wrap">

| **불변식**                                                              | **깨지면 무슨 일이 나는가**                     | **케이스** |
| -------------------------------------------------------------------- | ------------------------------------- | ------- |
| **보존** — 배분된 총량 + 남은 총량 == 초기 총량                                     | 출고 수량이 새거나 늘어 **고객별 배송현황·부분정산이 틀어진다** | 10,000  |
| **선택 규칙** — 항상 잔여가 충분한 **가장 앞선(오름차순) 주문라인** 에 매핑되고, 선택되지 않은 주문라인은 불변 | 귀속이 어긋나 「이 운송장이 어느 주문 건인가」를 다시 잃는다    | 10,000  |
| 🔴 **거절 시 무변경** — 단일 주문라인 잔여를 넘는 출고는 예외이며 **어떤 잔여도 바뀌지 않는다**         | 부분 차감이 남아 재시도 시 **수량이 이중 소모**된다       | 10,000  |
| **소진** — 전량 배분 후엔 어떤 양수 출고도 예외                                       | 잔여를 넘어 출고가 잡힌다                        | 2,000   |

</div>

<aside class="callout tone-orange" data-icon="🔒">

<strong>「거절 시 무변경」이 가장 중요하다.</strong>\
할당기는 잔여 목록을 순회하며 조건을 만족하는 항목에서만 차감하고, 못 찾으면 예외로 빠진다 — 즉 **부분 적용이 안 일어나는 것은 순회 구조에 의존**한다.\
리팩터링으로 차감을 루프 앞으로 옮기면 <strong>조용히 깨진다.</strong> 4번 결정(PO 라인 취소)의 「거절 시 무변경」과 같은 성질이라 같은 방식으로 잠갔다.

</aside>

<aside class="callout tone-gray" data-icon="🧭">

**경계 예시로 고정한 것** — 주문라인 정보 없음(마이너스 PO·레거시) → 없음 · 출고수량 0 이하 → 없음 + 불변 · 수량 0 이하·ID 없음·수량 없음 입력 무시 · **합포장 1행이 여러 주문라인에 걸치면 「출고 수량 1로 분할하라」는 신호** · 앞선 주문라인이 모자라 뒤로 넘어갔다가 **작은 출고가 오면 다시 앞을 쓴다**(단조 증가가 아니라는 점을 명시)

</aside>

### 그 밖에 검증한 계약

<div class="table-wrap">

| **대상**        | **테스트**                        | **고정한 것**                                                                                                       |
| ------------- | ------------------------------ | --------------------------------------------------------------------------------------------------------------- |
| 엑셀 양식 (3번 결정) | 양식 테스트 (관리자 4 · 공급사 3)         | **필수(연노랑) 표기 열과 파서가 읽는 열이 정확히 일치** — 인덱스 파서라 열 순서·헤더 문자열도 불변이어야 한다 · 관리자·공급사 양식 동형 · 「작성가이드」 기존 안내(합배송·분할출고) 보존 |
| 클레임 상태 축      | 상태 축 정책 테스트 (관리자 1 · 공급사 2)    | 클레임 상태는 **헤더에서 온다** — 라인 상태를 헤더 필드명으로 내보내지 않고, 집계 그룹키도 헤더 상태다(한 신청이 라인 단계별로 쪼개지지 않음)                            |
| 수거시작 알림       | 발주 서비스 테스트 (7)                 | 상품명 요약 경계(null·빈 리스트·1건·N건 → 「외 N-1건」) + 알림 데이터에 PO라인 기준 상품명 적재                                                 |
| 직거래 배제        | 직거래 필터 테스트 (5) · 예산 환원 테스트 (2) | 직거래 발주가 대행 목록에 섞이지 않고, 부분취소 예산 환원이 직거래 원장으로만 간다 — 상세는 「직거래 트랙」 카드 참조                                            |

</div>

### 이 검증이 말하지 않는 것

<aside class="callout tone-gray" data-icon="📐">

- **동시성은 증명되지 않았다** — 부분취소의 낙관적 동시성 가드(갱신 행 수 0 이면 충돌 예외)는 단위 테스트로 증명 불가하며 부하 테스트 영역이다. <strong>미수행.</strong>\
  • **라인 ↔ 배송 레코드 정합은 별도다** — 출고수량은 라인이 아니라 발주 배송 레코드에서 오므로 인자로 주입된다. 본 테스트는 그 계약을 사용할 뿐, <strong>두 테이블 간 합계 일치는 검증하지 않았다.</strong>\
  • **나머지 설계 결정은 여전히 미검증** — 합배송 운송장 자동전파, 배송완료 단일화, 배송추적 배치는 테스트가 없다. (엑셀 일괄출고는 **양식 계약만** 검증됐고 업로드 2-pass 로직은 미검증이다.)\
  → 주문라인 1:1 매칭은 **2026-08-30 불변식 검증으로 해소**됐다(위 절). 다만 그것도 **단위 레벨**이며, 접수→출고 전 경로가 실제 DB 에서 같은 귀속을 내는지는 별도다.

</aside>
