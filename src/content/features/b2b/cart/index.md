## 개요

B2B 전용몰 장바구니 기능. 단순 상품 담기가 아닌, **기업별 계약가·재고·행사를 실시간 반영**하는 동적 장바구니를 설계했다.

장바구니 진입 시 DB 프로시저가 모든 상품의 가격/재고를 일괄 갱신하여, 사용자에게 항상 최신 정보를 보여준다.

<aside class="callout tone-orange" data-icon="🔍">

<strong>이 기능에서 얻은 가장 큰 결론은 따로 있다 — 병목은 프로시저가 아니라 커넥션 풀이었다.</strong>

동시 100 VU 구간에서 HikariCP 는 **활성 20/20 포화 · 대기 75** 인데 <strong>MySQL CPU 는 1.3%</strong> 였다. DB 는 놀고 있었다.\
리틀의 법칙으로 교차 검증했다 — `20 커넥션 ÷ 161ms ≈ 124 req/s`, 실측 **146 req/s**.

→ 처리량을 막고 있던 건 **쿼리 튜닝이 아니라 풀 크기**였고, 그것을 알아낸 과정이 이 카드의 핵심이다. 아래 가격 동기화·왕복 절감은 그 결론에 도달하기 위한 경로다.

</aside>

## 왜 이 설계가 필요했는가 (Problem)

B2C 장바구니와 다른 B2B의 3가지 핵심 난제 — 단순 FK 참조 모델·애플리케이션 갱신으로는 해결 불가능했다.

<aside class="callout tone-scenario" data-icon="💸">

<strong>시나리오 1 — 가격 불일치 (정산 분쟁)</strong>

- **사용자가 장바구니에 담을 때 본 가격** — 12,000원
- **결제 진입 시 다시 조회** — 13,500원(가격 인상)

→ "왜 가격이 달라요?" 고객 항의 → 정산 분쟁 → 환불 요청\
→ <strong>장바구니에서 본 가격이 주문 가격으로 그대로 이어져야 한다.</strong>

</aside>

<aside class="callout tone-scenario" data-icon="🏢">

**시나리오 2 — 기업별 계약가 미반영**\
같은 상품이라도

- **A기업** — 정가
- **B기업** — −15% 할인 계약가

상품 정가만 보여주면 B기업 직원이 "이 가격 맞아? 우리 계약가 적용된 거 맞아?" 의심.\
→ 구매팀 문의 폭주\
→ <strong>장바구니 화면이 자동으로 기업별 계약가로 표시되어야 한다.</strong>

</aside>

<aside class="callout tone-scenario" data-icon="🐢">

**시나리오 3 — 갱신 비용이 상품 수에 비례한다**\
장바구니에 상품 50개 담은 사용자.\
갱신 로직을 상품당 조회하는 방식으로 짜면 — **실측: 장바구니 20개 기준 왕복 167회 · 응답 p50 395ms**\
→ 다만 이건 *순진하게 짠* 경우다. 묶을 수 있는 조회를 `IN` 절로 합치면 **30회 · p50 77ms** 로 줄어든다 — <strong>제대로 짜면 앱도 N+1 이 아니다.</strong>\
→ 그래서 **비교 기준을 167회가 아닌 30회로 잡았고**, 거기서도 남는 격차만 설계의 공으로 인정했다.

</aside>

이 3가지를 동시에 해결하기 위해 **DB 프로시저 + 장바구니 스냅샷 컬럼** 의 조합으로 결정했다.

## 테이블 설계

### 설계 배경 — 왜 5개 컬럼으로는 부족했나

초기 장바구니 테이블은 단순한 FK 참조 테이블이었다.

```text
-- 초기 설계: 단순 FK 참조
장바구니(장바구니 ID, 기업, 사용자, 상품, 수량)
```

B2B 전용몰의 장바구니는 B2C와 다른 요구사항이 있었다.

<div class="table-wrap">

| **B2B 요구사항**      | **문제**                       | **해결 → 추가된 컬럼**          |
| ----------------- | ---------------------------- | ------------------------ |
| 기업마다 계약 가격이 다름    | 상품의 판매가를 그대로 쓸 수 없음          | 판매단가 · 할인가 · 기업 계약가      |
| 주문 시점의 가격을 확정해야 함 | 장바구니 → 주문 전환 시 가격이 변동될 수 있음  | 정가 · 공급가 · 부가세 · 소비자가    |
| 행사/쿠폰 할인액을 분리 추적  | 할인 출처별 금액을 구분해야 정산 가능        | 행사 할인 · 자동 쿠폰 · 수동 쿠폰 금액 |
| 공급사별 묶음배송 그룹핑     | 장바구니 화면에서 공급사별로 상품을 그룹핑 표시   | 공급사 · 공급사명 · 묶음배송 그룹     |
| 프로시저 계산 결과 저장     | 프로시저가 계산한 가격/수량/상태를 장바구니에 기록 | 스냅샷 컬럼 전체 (가격/상품/공급사)    |

</div>

이 요구사항들을 반영하면서 5개 컬럼짜리 참조 테이블이 **가격 · 상품 · 공급사 스냅샷을 담는 수십 개 컬럼**으로 확장되었다.

### 장바구니 최종 구조

| 공급사 스냅샷  | 공급사 · 공급사명 · 사업자번호             | 공급사별 그룹핑 표시에 활용                    |

| 할인/쿠폰    | 행사 할인 · 자동 쿠폰 · 수동 쿠폰          | 행사할인과 쿠폰을 분리하여 금액 추적               |
| 그룹핑      | 묶음배송 그룹 · 선택형 그룹               | 묶음배송 그룹, 선택형 그룹 지원                 |
| 사용자 상호작용 | 선택 여부 · 수량 · 메모                | 선택 상태, 수량, 메모를 개별 관리               |

</div>

<aside class="callout tone-blue" data-icon="💡">

**스냅샷 컬럼의 핵심 역할**: 장바구니 갱신 프로시저가 계산한 결과(기업별 계약가, 할인액, 조정된 수량)를 **저장할 대상 컬럼**이다. 이 데이터는 주문 생성 프로시저가 그대로 읽어 **주문 시점의 가격을 확정**하는 데 활용된다.

</aside>

### 왜 스냅샷 컬럼이 필요했나

스냅샷 컬럼 없이도 기능 자체는 구현할 수 있다. 장바구니 조회 시 상품 · 기업별 상품(계약가) · 기업 테이블을 매번 JOIN하거나, 주문 생성 시 그 시점에 직접 상품/가격을 조회하면 된다.

그러나 **스냅샷 컬럼과 프로시저는 세트**다.

<div class="table-wrap">

| <strong>스냅샷 없이 (애플리케이션에서 직접)</strong>              | <strong>스냅샷 + 프로시저 (현재 설계)</strong>                  |
| -------------------------------------------------- | ---------------------------------------------------- |
| 갱신 로직을 애플리케이션에서 구현<br>→ 상품당 3회 쿼리 (N+1 문제)         | 프로시저가 DB 내부에서 일괄 갱신<br>→ 1회 CALL로 완결                 |
| 프로시저가 계산 결과를 저장할 곳이 없음<br>→ 임시 테이블 또는 OUT 파라미터로 반환 | 프로시저가 장바구니 스냅샷 컬럼에 직접 UPDATE<br>→ 별도 반환 로직 불필요       |
| 주문 생성 시 가격을 다시 조회해야 함<br>→ 장바구니와 주문 사이 가격 불일치 가능   | 주문 생성 시 장바구니 스냅샷을 그대로 사용<br>→ 장바구니에서 본 가격 = 주문 가격 보장 |

</div>

<aside class="callout tone-purple" data-icon="🔗">

프로시저로 갱신 로직의 N+1을 해결하려면 계산 결과를 **저장할 스냅샷 컬럼**이 필요했고,\
스냅샷 컬럼이 있으니 주문 생성 시에도 그 데이터를 **그대로 활용**할 수 있게 되었다.\
→ 두 가지가 서로를 필요로 하는 **상호 보완적 설계**다.

</aside>

## 핵심 설계 결정 — 장바구니 갱신 프로시저

<aside class="callout tone-orange" data-icon="⚙️">

<strong>왜 프로시저인가?</strong>\
장바구니 진입 시 모든 상품의 가격/재고를 한번에 갱신해야 한다.

- **애플리케이션 레벨** — 상품 수만큼 N+1 쿼리 발생
- **DB 프로시저** — **커서 기반 일괄 처리**로 네트워크 라운드트립 없이 DB 내부에서 완결

</aside>

### 검토했던 대안들 (Analyze)

"장바구니 진입 시 모든 상품의 최신 가격·재고 동기화"를 위한 5가지 방법을 비교했다.

<div class="table-wrap">

| **대안**                          | **장점**                                     | **기각 사유**                                                             |
| ------------------------------- | ------------------------------------------ | --------------------------------------------------------------------- |
| 1. 매번 조회 시 JOIN (실시간 계산)        | 스냅샷 불필요, 항상 최신                             | 장바구니 조회 빈도 높음 → 매번 상품 · 기업별 상품 JOIN 수행 비용. 주문 생성 시점과 가격 불일치 위험 여전히 존재 |
| 2. Redis 가격 캐싱 (TTL 5분)         | 빠른 조회, 캐시 적중률 높음                           | 가격 변동 시점과 캐시 만료 사이 정합성 깨짐. 기업별 계약가 캐시 키 폭증(M기업 × N상품). Redis SPOF     |
| 3. 비동기 스케줄러 갱신 (5분 주기)          | 장바구니 조회 부하 0                               | 사용자가 본 시점과 갱신 시점 차이 → 가격 불일치 동일 발생. "왜 어떤 사람만 이전 가격?" 디버깅 난해          |
| 4. 애플리케이션 + 배치 로딩 (Batch Fetch) | JPA 유지하면서 N+1 회피                           | 여전히 외부 호출 발생. 가격 계산·재고 조정 로직이 Java에 분산 → 주문 생성 프로시저와 로직 중복            |
| 5. DB 프로시저 + 장바구니 스냅샷           | 1회 RT, 가격·재고·계약가 DB 내부 완결, 주문 생성 시 스냅샷 재사용 | DB 종속성, 프로시저 디버깅 비용 (수용 가능)                                           |

</div>

<aside class="callout tone-green" data-icon="✅">

<strong>선택: 5번 (DB 프로시저 + 스냅샷)</strong>\
응답속도·가격 정합성·로직 단일화 3가지 축에서 가장 유리.\
특히 **주문 생성이 스냅샷을 그대로 재사용**하므로 "장바구니에서 본 가격 = 주문 가격" 보장이 자연스레 따라온다.

**단, 맹신은 아니다**\
주문 생성은 스냅샷을 쓰되 **주문 시점에 현재 상품가와 재검증**하여, 장바구니 조회→주문 사이 가격이 바뀌었으면 가격 변경 오류로 **차단하고 장바구니 새로고침을 유도**한다.\
→ **스냅샷 재사용 + 변동 시 차단의 2중 안전망**

</aside>

### 비교: 애플리케이션 레벨 vs DB 프로시저

#### ❌ 애플리케이션 레벨로 구현했다면

장바구니 아이템 N개를 순회하며 **상품당 3회 쿼리**(상품 조회 → 계약가 조회 → UPDATE)가 발생한다.

```text
// 애플리케이션 레벨로 갱신한다면 (가정한 의사코드)
장바구니 = 사용자 · 기업의 장바구니 조회  // 1회
for 항목 in 장바구니:  // N개 순회
    상품 = 상품 최신 정보 조회(항목)  // N회
    if 상품 없음 또는 판매중지: 항목 삭제 표시, 다음 항목으로
    계약가 = 기업별 계약가 조회(항목, 기업)  // N회
    할인가 = 할인 계산(정가, 할인율)  // 메모리에서 계산
    수량 = 재고 · 최대 주문수량에 맞춰 조정
    장바구니 스냅샷 갱신(할인가, 계약가, 수량)  // N회
// 총 쿼리: 1 + 3N (상품 20개 → 61회)
```

<aside class="callout tone-red" data-icon="⚠️">

**실측**: 상품 20개 기준 **왕복 167회**. 다만 이건 *순진하게 짠* 경우고, **묶을 수 있는 조회를** `IN` **절로 합치면 30회로 줄어든다**(라인 수 무관 상수). 비교는 후자를 기준으로 삼았다.

</aside>

#### ✅ DB 프로시저로 구현한 결과

단 **1회 CALL**로 DB 내부에서 커서 기반 일괄 처리한다.

```text
-- 장바구니 갱신 프로시저 (요지)
FOR 항목 IN (사용자 · 기업의 장바구니) LOOP  -- 커서로 DB 안에서 순회
    상품 정보 조회 · 판매 가능 검증  -- DB 내부 호출, 네트워크 왕복 없음
    기업별 계약가 조회
    할인가 = FLOOR(정가 × (1 − 할인율 / 100))
    수량 = 재고 · 최대 주문수량에 맞춰 조정
    UPDATE 장바구니 SET 판매단가 · 할인가 · 계약가 · 수량 …
END LOOP
```

<aside class="callout tone-green" data-icon="✅">

**핵심**: 커서 내부의 SELECT·UPDATE는 모두 **DB 엔진 내부 호출**이므로 네트워크 비용이 0이다. 애플리케이션은 프로시저를 **1회만** 호출하면 된다.

</aside>

### 성능 비교 (장바구니 상품 20개 기준)

<div class="table-wrap">

| **항목**      | **애플리케이션 레벨**                                | **DB 프로시저**                                | **개선 효과**    | **측정 방법**                                                            |

| 네트워크 라운드트립  | **30회** (`IN` 절 배치)<br>**167회** (상품당 조회)     | **4회**                                     | 배치 대비 26회 절감 | <span class="chosen-mark">✅</span> **실측 완료** — MySQL 전역 카운터 델타       |

| 응답 시간       | 반복 RT 누적                                     | **p95 78ms** (무경합) / **600ms** (동시 100 VU) | —            | <span class="chosen-mark">✅</span> **실측 완료** (k6, 아래 Result)         |
| 상품 50개 시    | 왕복은 **라인 수와 무관한 상수**<br>(`IN` 절로 묶으면 30회 고정) | **4회 고정**                                  | 격차는 일정하게 유지  | <span class="chosen-mark">✅</span> 실측 — 제대로 짜면 앱도 N+1 이 아니다          |

</div>

<aside class="callout tone-gray" data-icon="📐">

**수치 투명성**

- **응답시간·커넥션 거동** — ✅ k6 + Prometheus 로 **실측 완료** (아래 Result)
- **라운드트립** — 세 구현을 실제로 만들어 MySQL 전역 카운터 델타로 **실측**했다 (167 · 30 · 4회). 위 의사코드의 "1 + 3N = 61회"는 쿼리 수를 센 값이라 비교에 쓰지 않는다.

→ <strong>실측치와 계산값을 섞지 않고 분리해 제시한다.</strong>

</aside>

<aside class="callout tone-blue" data-icon="📊">

**세 구현의 실측 비교** (장바구니 20개)

- **상품당 조회** — 왕복 167회 · p50 395ms
- `IN` **절로 묶음** — 왕복 30회 · p50 77ms — 제대로 짜면 앱도 N+1 이 아니다
- **프로시저** — 왕복 4회 · p50 20ms

→ 운영급 왕복 지연(1ms)을 주입하면 **31.7ms vs 139.9ms — 4.4배**. 네트워크가 멀어질수록 벌어진다.

</aside>

### 병목은 프로시저가 아니라 커넥션 풀이었다

부하 구간의 서버측 지표가 병목 위치를 특정했다.

<div class="table-wrap">

| **지표**      | **값**   | **해석**                  |
| ----------- | ------- | ----------------------- |
| HikariCP 활성 | 20 / 20 | 풀 포화                    |
| HikariCP 대기 | 75      | 동시 100 요청 중 75개가 커넥션 대기 |
| MySQL CPU   | 1.3 %   | **DB 는 놀고 있음**          |
| 행 잠금 대기 증가  | 53건     | 잠금 경합 아님                |

</div>

<aside class="callout tone-green" data-icon="✅">

리틀의 법칙과도 일치한다 — `20 커넥션 ÷ 161ms ≈ 124 req/s` (실측 146).\
→ 처리량 한계를 만든 것은 **프로시저 실행 시간이 아니라 커넥션 풀 크기**였다.\
풀을 5 → 20 으로 바꿔 대조 측정했을 때도 동일한 구조(활성 포화 + MySQL 유휴)가 재현되었다.

</aside>

### 트랙 순도 가드 검증

<aside class="callout tone-evidence" data-icon="🧪">

장바구니가 **가격 동기화**만 책임지던 데서, 직거래 트랙이 들어오면서 **선택 단계의 게이트** 역할이 추가됐다.\
트랙 순도 테스트 · **6/6 통과**

- 대행 + 직거래가 함께 선택되면 거부하고 **선택 상태를 저장하지 않는다**
- 판정이 막힌(차단) 상품은 직거래 쪽으로 묶는다 — 대행 폴백 금지
- **선택 해제는 검사하지 않는다** — 내리는 동작은 혼합을 만들 수 없다
- 선택 상품이 1건 이하면 **판정 자체를 호출하지 않는다** (섞일 수 없음 — 불필요 쿼리 제거)

자세한 판정 규칙은 「직거래 트랙」 카드 참조.

</aside>

### 이 재측정이 말하지 않는 것

<aside class="callout tone-gray" data-icon="📐">

- 🔴 **위 표를 「8월 중순 측정」과 직접 비교하면 안 된다** — 기존 수치(p95 78ms 무경합 / 600ms @100VU)는 **구간을 분리**해 뽑은 값이고, 재측정은 워밍업·램프가 섞인 **전 구간 집계**다. 집계 창이 달라 개선폭을 계산할 수 없다. <strong>풀 5 ↔ 20 비교만 같은 축이라 유효하다.</strong>\
  • **풀 포화 피크를 못 잡았다** — 기존의 <em>활성 20/20 · 대기 75 · MySQL CPU 1.3%</em> 에 해당하는 지표를 이번엔 수집하지 못했다(샘플러 결함). 부하 종료 후 대기 요청은 0 이라 사후 회수도 불가능하다. → 처리량·지연 대조로만 병목을 주장한다.\
  • **측정 시점의 스키마·프로시저가 8월 중순과 다르다** — 그 사이 스키마 변경이 반영됐고 프로시저 정의도 갱신됐다. 절대 수치의 시계열 비교는 이 변경을 감안해야 한다.

</aside>

### 이 측정이 말하지 않는 것

<aside class="callout tone-gray" data-icon="📐">

- **운영 환경이 아니다** — 로컬 단일 인스턴스·컨테이너 MySQL. 운영 DB·다중 인스턴스·혼합 트래픽 조건이 아니므로 <strong>절대 처리량으로 읽으면 안 된다.</strong>\
  • **100 VU ≠ 동시 사용자 100명** — 생각시간이 없어 항상 100개 요청이 처리 중인 상태다. 실사용으로 환산하면 훨씬 큰 규모에 해당한다.\
  • **왕복 지연은 주입값이다** — 운영의 실제 앱↔DB 지연을 모르므로 0·1·2·5ms 범위를 가정해 곡선을 얻었다. 그 범위 밖으로 외삽하면 안 된다.

</aside>
