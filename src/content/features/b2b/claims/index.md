## 개요

B2B 전용몰의 **취소·반품·교환 전체 프로세스**를 담당하는 기능. 주문(SO)·발주(PO)와 맞물려 **구매자 신청 → 공급사 처리(승인·수거·검수·환불/재배송) → 관리자 감독**의 3주체 워크플로우를 단일 도메인으로 설계했다.

배송 전 **취소**, 배송 후 **반품**(환불), **교환**(맞배송)을 하나의 클레임 모델로 통합하되, 물리 처리(수거·검수·재배송)는 **라인·박스 단위로 독립 추적**한다.

<div class="table-wrap">

| **헤더-라인-수거 3계층**       | **3개 유형 / 32개 상태**   | **마이너스 PO 정산**     | **포인트 FIFO 환수**    |
| ---------------------- | -------------------- | ------------------ | ------------------ |
| 신청 · 실무 처리 · 물류 단위를 분리 | 취소 5 · 반품 13 · 교환 14 | 원 PO 불변 + 음수 PO 생성 | 만료 가드 + FOR UPDATE |

</div>

## 왜 이 설계가 필요했는가 (Problem)

B2B 클레임은 단순 환불이 아니다 — **부분 출고·여러 공급사·여신/포인트 결제·정산 추적**이 얽혀, 단일 테이블·단순 환불 로직으로는 정합성이 깨진다.

<aside class="callout tone-scenario" data-icon="🎯">

**시나리오 1 — 부분 반품 누적 정산 오차**\
상품 10개(실결제 33,333원, 할인·쿠폰·포인트 혼재)를 3개 → 3개 → 4개로 나눠 반품.\
단가 × 수량으로 계산하면 매번 반올림 오차가 쌓여, 전량 반품했는데 **환불 합계가 원결제액과 1원 어긋난다**.\
→ **정산 불일치 · CS 분쟁**

</aside>

<aside class="callout tone-scenario" data-icon="📦">

**시나리오 2 — 반품/교환의 발주(PO) 정산**\
주문 시 생성된 공급사 발주(PO) 기준으로 매출/정산이 집계된다.\
반품 시 원 PO를 직접 차감(UPDATE)하면 **발주 이력이 파괴**되고, 부분취소가 누적되면 원본 금액을 복원할 수 없다.\
→ **공급사 정산 근거 소실**

</aside>

<aside class="callout tone-scenario" data-icon="💸">

**시나리오 3 — 포인트 환수와 만료**\
고객이 사용한 포인트를 환불 시 복원해야 한다. 그런데 사용 당시엔 유효했지만 클레임 시점에 **이미 만료된 포인트**가 있다.\
무조건 복원하면 만료 포인트가 부활하고, 무시하면 고객 손실을 추적할 수 없다.\
→ 게다가 동시 환수 시 **이중 복원** 위험

</aside>

<aside class="callout tone-scenario" data-icon="🚚">

**시나리오 4 — 부분 출고 주문의 박스 단위 수거**\
한 주문 라인이 여러 발주 배송(박스)으로 분할 출고되거나, 여러 박스를 한 번에 합포장 수거해야 한다. 라인 단위로만 수거 송장을 관리하면 **같은 박스에 중복 송장**이 붙거나, 박스별 진행 상태를 표현할 수 없다.

</aside>

이 난제들을 **헤더-라인-수거 3계층 + 마이너스 PO + 잔여 기준 금액 배분 + FIFO 포인트 환수**의 조합으로 해결했다.

## 테이블 설계 — 헤더-라인-수거 3계층

<aside class="callout tone-blue" data-icon="💡">

<strong>왜 3계층으로 분리했는가?</strong>

- **헤더** — 클레임 신청 1건 단위. 헤더만 보는 **구매자 화면**의 모델
- **라인** — SKU·분할 단위. 수거→검수→반송/재배송이 라인별 **독립 진행** — **공급사 실무 화면**의 모델

→ 세 주체의 화면을 **한 모델로 만족**시키기 위한 분리

</aside>

## 상태 머신 — 유형별 (취소 / 반품 / 교환)

<aside class="callout tone-orange" data-icon="⚙️">

유형마다 상태 집합이 다르다.

- **취소 5개** — 물리 흐름 없음
- **반품 13개** — 수거·검수·반송 추가
- **교환 14개** — 재배송까지

라인 상태가 바뀌면 **활성 라인 중 가장 뒤처진(laggard) 상태**를 헤더에 sync — 구매자에게 항상 "현재 진행 중인 단계"가 보인다.\
※ 아래 그림은 주요 흐름만 그렸다 — 상태 수는 유형별 전체 기준이라 그림에 없는 갈래가 있다.

## 핵심 설계 결정

### 1. 부분 클레임 금액 배분 — 잔여 비례 + 마지막 흡수

<aside class="callout tone-orange" data-icon="🎯">

순차적 부분 클레임이 **합산되어도 원결제액과 정확히 일치**하도록:

- 각 시점의 **잔여금액 / 잔여수량** 기준으로 계산 (원본 기준 아님)
- 마지막 클레임(잔여수량 0)에서 **끝수를 전부 흡수**
- 한 번 배분한 값은 라인에 **영구 저장** — 환불·포인트 환수 때 재사용 (재계산 금지)

</aside>

#### 검토한 대안 (Analyze)

<div class="table-wrap">

| **대안**                               | **장점**                                                               | **단점**                                                                                                                                                                     | **선택**                                |
| ------------------------------------ | -------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------- |
| 1. 단가 × 클레임수량                        | 계산 단순·직관적                                                            | 할인·쿠폰·포인트가 섞인 실결제액과 불일치. 매 클레임 반올림 오차 누적                                                                                                                                   | ❌                                     |
| 2. 매번 (실결제액 × 비율) 재계산                | 항상 원본 기준이라 계산 근거 단순                                                  | 라운딩 차이 누적 → 전량 반품 시 원금 불일치, **다음 클레임 잔여가 음수**가 되는 버그                                                                                                                       | ❌                                     |
| 3. 잔여 비례 + 10원 내림 + 마지막 흡수 + 저장값 재사용 | Σ(배분액) = 원결제액 **정확 일치** 보장. 부분 클레임의 차이(최대 10원)는 누적되지 않고 마지막 클레임에서 정산 | ① 회차별 금액이 **순서 의존** — 같은 수량도 회차마다 환불액이 다를 수 있고 마지막 회차가 끝수 흡수(CS 안내 필요) ② "기청구 수량/금액" 집계 정확성에 전체가 의존 — 활성 클레임만·분할 라인 이중집계 방지가 전제 ③ 배분값 영구 저장 관리 부담 — 저장값·재계산값 드리프트 금지 규칙 필요 | <span class="chosen-mark">✅</span> 선택 |

</div>

> **판단 기준은 오차의 크기가 아니라 소멸 여부** — 대안 1·2의 오차는 합계가 원결제액과 **영구히 불일치**하는 정산 오차이고, 채택안의 최대 10원은 중간 회차의 **일시적 차이**로 전량 클레임 완료 시 합계가 정확히 일치한다(마지막 흡수로 정산).

```text
잔여금액 = 총금액 − 기청구금액
잔여수량 = 총수량 − 기청구수량
if 잔여금액 ≤ 0 또는 잔여수량 ≤ 0: return 0  // 잔여 없음
if 요청수량 ≥ 잔여수량: return 잔여금액  // 마지막 클레임 = 잔여 전부 흡수
배분 = 잔여금액 × 요청수량 / 잔여수량  // 정수(long) 연산으로 overflow 방지
return 10원 단위 내림(배분)  // 부분 클레임 = 10원 단위 내림
```

<aside class="callout tone-green" data-icon="✅">

- 금액·VAT·쿠폰·구매포인트·지급포인트 **5개 차원에 동일 규칙** 적용\
  • "이미 청구된 수량/금액"은 **거절·철회를 제외한 활성 클레임만** 집계\
  • 분할되지 않은 **원본 라인 기준** — 분할 보정 라인의 **이중 집계 방지**

</aside>

<aside class="callout tone-evidence" data-icon="🧪">

<strong>Property 테스트 검증 (jqwik 1.9.2)</strong> — 공통 모듈의 금액 배분 테스트 · **10/10 통과**\
랜덤 시나리오(원결제액 ≤10억 × 총수량 ≤300 × 분할 ≤10회) — **불변식 4개 × 각 10,000케이스**:\
① 전량 클레임 완료 시 **Σ배분액 == 원결제액**\
② 어떤 시점에도 배분액 ≤ 잔여 (**잔여 음수 불가**)\
③ 부분 클레임은 **10원 배수** + 정확 비례값과 차이 10원 미만\
④ **소액 차원**(쿠폰·포인트, 0원 포함)에서도 동일 성립

**기각 대안 2 반증** — 동일 property에 넣으면 5번째 시도에서 반례 검출:

- shrinking 27단계 → 최소 반례 `1원·2개·[1+1]`: round(0.5)=1 이 두 번 → 2원 배분 (1원 초과, "잔여 음수" 버그 재현)
- 랜덤 원본 반례: 262,891원·58개·10회 분할 → 합계 262,890원 (1원 유실)
- 33,333원 3·3·4 시나리오와 기각 대안 반례는 example로 회귀 고정

<strong>기청구 집계 슬라이스 검증 (@MybatisTest · H2 MySQL 모드)</strong> — 기청구 집계 테스트 · **12/12 통과**

- 거절·철회 제외 / 분할 원본의 이중집계 방지 / 기업 격리 / 배송 단위 스코프(NULL 제외) 전수 검증
- property 테스트의 전제("집계값이 정확하다면")를 실증 — 계산(property) + 집계(슬라이스) 양쪽 증거 완성

⚠️ **검증 과정에서 실제 결함 검출** — 가용수량 집계 쿼리에만 분할 원본 필터가 누락되어, 분할검수 후 부모+자식 이중집계(9→13)로 정당한 추가 클레임이 "가용수량 초과"로 차단될 수 있었음 → 자매 쿼리와 동일 필터로 수정하고 테스트로 회귀 고정

⚠ property 테스트도 전수 탐색은 아님 — 수학적 증명이 아니라 <strong>"반례를 적극 탐색했으나 발견되지 않음"</strong>의 경험적 증거.

</aside>

### 2. 마이너스 PO — 원 PO 불변 + 음수 발주로 정산 순액 자동화

<aside class="callout tone-green" data-icon="📦">

반품/교환 승인 시 원 발주(PO)를 수정·삭제하지 않고 **별도의 음수(-) PO를 생성**한다.

- 정산/매출 집계 = PO 기준 <strong>순액 = Σ(원 PO + 마이너스 PO)</strong> 자동 산출
- 교환 = 수거용 마이너스 PO + 재배송용 플러스 PO **쌍 → 순액 0**

</aside>

#### 검토한 대안 (Analyze)

<div class="table-wrap">

| **대안**                    | **장점**                                        | **단점**                                    | **선택**                                |
| ------------------------- | --------------------------------------------- | ----------------------------------------- | ------------------------------------- |
| 1. 원 PO 직접 차감(UPDATE)     | 테이블 단순                                        | 발주/매출 이력 파괴, 부분취소 누적 시 원본 복원 불가, 정산 추적 불가 | ❌                                     |
| 2. 원 PO soft-delete 후 재생성 | 이력 일부 보존                                      | 발주 연속성·PG/배송 참조 단절                        | ❌                                     |
| 3. 마이너스(-) PO 별도 생성       | 원 PO 불변, 순액 자동 산출, 정산/매출 PO 기준 일관, 양방향 참조로 추적 | 행 증가, 부호 정합 관리 필요                         | <span class="chosen-mark">✅</span> 선택 |

</div>

```text
// 헤더·라인의 모든 금액 필드를 음수로 통일 → 정산 합산이 깨지지 않음
마이너스 PO.주문금액 = −클레임 총액
마이너스 PO 라인.수량 = −클레임 수량
마이너스 PO 라인.공급가 = −공급가,  부가세 = −부가세
마이너스 PO 라인.결제금액 = −클레임 금액  // 결제금액은 VAT 포함 → 부가세를 따로 더하지 않음(이중계산 방지)
클레임.마이너스 PO = 마이너스 PO  // 클레임 ↔ 마이너스 PO 양방향 참조
```

<aside class="callout tone-gray" data-icon="🛡️">

**부호 정합·호환성**

- 공급가/VAT는 항상 **절댓값**으로 계산, 호출자가 방향 적용 (반품=음수, 재배송=양수)
- 부호 정책 변경(2026-05-07) 이전 데이터 호환용 절댓값 처리 안전망
- 전체 검수 불합격 시 마이너스 PO **취소 처리**

</aside>

### 3. 포인트 FIFO 역추적 환수 + 만료 가드

<aside class="callout tone-blue" data-icon="💸">

사용 포인트를 **사용이력 최신순(FIFO 역순)으로 조회**하여 원장에 복원한다.

- **만료 가드** — 사용 당시 유효했으나 클레임 시점 만료된 버킷은 소생시키지 않고 **손실로 분리 기록** (환불 실패 행)
- **동시성 보호** — `FOR UPDATE` 잠금으로 동시 환수 시 **이중 복원 차단**

</aside>

```text
// 사용이력 버킷을 최신순으로 채우며 복원액 = min(남은 환수액, 버킷 사용액)
for 버킷 in 사용이력(최신순):
    복원액 = min(남은 환수액, 버킷 사용액)
    if 버킷 만료일 < 오늘:
        만료손실 += 복원액  // 만료 버킷: 소생 불가 → 손실로 분리
    else:
        원장 잔액 복원(버킷, 복원액) + 환불 이력 기록  // 유효 버킷만 복원
    남은 환수액 −= 복원액
```

<aside class="callout tone-green" data-icon="✅">

- 환수 금액은 신청 시 배분해 둔 **저장값을 그대로 사용** — 재계산 금지 (라운딩 차이로 잔여가 음수가 되는 버그 방지)\
  • 결과는 실복원분(완료) / 만료손실분(실패, 사유: 사용기간 만료) **두 개의 환불 내역 행**으로 기록\
  • 포인트는 여신/PG 환불과 **독립** 처리

</aside>

<aside class="callout tone-evidence" data-icon="🧪">

**단위 테스트 검증** — 공통 모듈의 포인트 환수 테스트 · **7/7 통과**\
예시 6 + 보존식 property (랜덤 버킷 구성 × 만료 여부 × 요청액, 2,000케이스):\
① <strong>min(잔여, 사용액)</strong> 순서 소진 + 환불 이력 기록\
② 만료 버킷 **미소생** (원장 UPDATE·잠금 0건) + 손실 분리 — **유효 버킷이 만료 몫을 대체 복원하지 않음**\
③ **보존식**: 실복원 + 만료손실 == 환수 요청액 (누수·이중복원 없음, 보고값 == 원장 반영액)\
④ 만료일 **당일은 아직 유효** (경계)\
⑤ 구매 포인트 / 지급 포인트 **차원 독립** 복원\
⑥ 사용이력 부족 시 **예외**로 정합 보호

<strong>범위 밖 (별도 수단)</strong>

- `FOR UPDATE` 동시 환수 이중 복원 차단 — 단위 테스트 증명 불가, **부하테스트+DB assertion** 영역
- 사용이력 역순 정렬 자체 — 조회 쿼리의 **ORDER BY 책임** (슬라이스 영역). 본 테스트는 "반환된 순서대로 소진"까지 보장

</aside>

### 4. 헤더-라인 상태머신 + 이력 단일화

<aside class="callout tone-orange" data-icon="🔀">

- **전이 검증** — 엔티티 도메인 메서드가 책임 (현재 상태 가드 + 예외)\
  • **이력 INSERT** — 상태 머신의 이력 기록 메서드 **하나로** 위임. 관리자·공급사·구매자 3개 채널이 각자 작성하던 상태 이력 INSERT 중복(31개 메서드)을 하나로 통합\
  • **라인→헤더 sync** — **진행 단계가 가장 낮은(laggard) 라인**을 헤더 대표 상태로 선택

</aside>

<aside class="callout tone-gray" data-icon="📐">

**범위 정확성**

- 이력 단일화 적용 범위 = 3개 채널의 **동기 전이** 경로
- 배송완료 감지 같은 **배치 완료 전이**는 MyBatis 직접 UPDATE (별도 경로)

→ "모든 전이가 단일 진입점"이 아니라 <strong>"3개 동기 채널의 전이를 단일화"</strong>가 정확한 표현

</aside>

### 5. 합포장 수거 — 2단계 승인 + DB 레벨 중복 차단

<aside class="callout tone-blue" data-icon="🚚">

수거 단위를 라인이 아닌 <strong>수거(박스)</strong> 로 격상.

- 송장 등록/수정/취소를 수거 1건에 하면 하위 라인에 **일괄 전파**
- 합포장(여러 원배송 → 한 박스)은 **고객 요청 → 관리자 승인** 2단계
- 동일 배송 중복 수거는 DB **생성 컬럼 + UNIQUE**로 원천 차단 (우선순위: 번들 > 단일배송 > 합포장)

</aside>

```text
-- 수거 중복 키: DB 가 계산해 저장하는 생성 컬럼 (GENERATED … STORED)
중복키 = CASE 합포장이면 'C:'
             번들 배송이면 'B:' + 번들 키
             그 밖이면 'D:' + 원배송 ID END
UNIQUE (클레임, 중복키, 삭제여부)  -- 같은 배송을 두 번 수거할 수 없다
```

<aside class="callout tone-gray" data-icon="📥">

**엑셀 일괄 처리**

- 수거/재배송 리스트 다운로드 → 택배 프로그램 송장 발급 → 업로드 일괄 등록 (수거 1건 = 엑셀 1행)
- 검수 합격분 재배송 PO는 **클레임당 1건**으로 묶어 생성 — flush 타이밍 버그(라인 수만큼 PO 중복 생성) 제거

</aside>

### 검증이 실제 결함을 잡았다

<aside class="callout tone-red" data-icon="🐛">

테스트를 짜는 과정에서 **살아있는 버그를 발견**했다.\
가용수량 집계 쿼리에만 분할 원본 필터가 누락돼, 분할검수 후 **부모+자식이 이중 집계**(9 → 13)되어 **정당한 추가 클레임이 "가용수량 초과"로 차단**될 수 있었다.\
→ 자매 쿼리와 동일 필터로 수정하고 테스트로 회귀 고정.

</aside>

> 불변식을 세우자 **설계가 아니라 구현의 구멍이 드러난** 사례다. 예시 테스트만 짰다면 분할검수 × 추가클레임이라는 조합을 떠올리지 못해 놓쳤을 것이다.

<aside class="callout tone-red" data-icon="🐛">

**두 번째 결함 — 전량 교환 후 반품이 0원으로 배분됐다**\
교환을 기청구 풀에서 제외하지 않으면, 전량 교환을 마친 뒤 **재배송분을 반품**할 때 배분 풀이 이미 비어(0,0) 있어 **환불액이 0원**이 된다.\
→ 수량과 금액 5컨럼이 **원자적으로 함께** 빠지도록 고치고, **수정 전 결함을 재현하는 테스트까지 남겨** 되돌리면 바로 깨지게 했다.

</aside>

<aside class="callout tone-red" data-icon="🐛">

**세 번째 결함 — 반려·철회분이 발주라인 집계에 섞였다**\
발주라인의 클레임 수량 조각을 계산할 때 **헤더축 필터가 없으면** 반려 4 + 철회 5 가 섞여 5 가 아니라 **14** 로 집계된다.\
→ 클레임 헤더 축 조인을 강제하고, **헤더 집합을 라인 컬럼에 걸지 않는다**는 축 드리프트 가드를 별도 테스트로 잠갔다.

</aside>

**이 실측의 한계 — 지나치게 읽지 말 것**

- 🔴 `FOR UPDATE` **단독의 기여를 분리하지 못했다** — 실험 ① 의 거절 19건은 **주문 상태 가드가 상류에서** 막은 것이어서 환수 지점에 도달하지도 않았다. 즉 실사용 방어는 **상태 가드가 1선**이고, 원장 잠금은 그 뒤의 방어층이다.
- **포인트 사용이력을 시드로 심었다** — 주문 API 의 실제 포인트 결제 경로를 타서 생성한 게 아니라, 포인트 사용이력과 라인의 포인트 사용액을 직접 적재했다. 환수 경로 자체는 실제 코드다.
- **만료 버킷 손실 분리는 재지 않았다** — 버킷 만료일을 미래로 둔 구성이라 단위 테스트가 덮는 만료 경로는 이번 부하에 포함되지 않았다.
- **로컬 단일 인스턴스** — 운영 규모가 아니다.

</aside>
