## 한 주문, 여러 공급사

B2B 몰의 주문 하나에는 여러 공급사의 상품이 섞인다. 공급사 A는 출고를 마쳤는데 B는 재고가 없어 취소했고 C는 아직 처리 중일 수 있다. 주문 하나에 상태 하나로는 "이 주문은 지금 어떤 상태인가"에 답할 수 없고, 공급사별로 정산할 수도 없다. 그래서 <strong>고객 주문(SO)과 공급사 발주(PO)를 나눴다.</strong>

<figure class="diagram"><img src="/content-assets/b2b/order-payment/diagram-1.light.svg" alt="한 주문, 여러 공급사 다이어그램" class="diagram-light" loading="lazy" decoding="async"><img src="/content-assets/b2b/order-payment/diagram-1.dark.svg" alt="한 주문, 여러 공급사 다이어그램" class="diagram-dark" loading="lazy" decoding="async"></figure>

- 발주는 결제가 확정된 뒤 주문 라인의 공급사를 기준으로 자동으로 나뉜다. 공급사마다 배송 추적 · 입고 확인 · 취소 · 정산을 따로 한다.
- 발주 라인은 구매자가 취소한 수량과 공급사가 취소한 수량을 따로 센다. 누구 귀책인지를 두고 정산 분쟁이 생기지 않게 하려는 것이다.
- 주문 시점의 상품명 · 가격 · 이미지, 주문자 · 기업, 공급사 정보를 주문 쪽에 복사해 둔다. 나중에 가격이 바뀌어도 지난 주문은 그대로다.\
  공급사 항목을 주문 한 행에 JSON 으로 넣는 안은 공급사 하나의 상태가 바뀔 때마다 주문 행 전체를 고쳐 충돌하고, 공급사별 상태만 따로 두는 안은 주문 본체와 상태 테이블의 정합성을 맞추기 어려워 고르지 않았다.\
  상태도 두 층이다. 주문(SO)은 아래 13개 상태를 따라가고, 발주 라인은 공급사별로 따로 배송 상태(대기 → 배송중 → 배송완료)를 가진다. 주문 전체가 '배송중'이어도 라인마다 배송 상태가 다를 수 있다.

## 주문 생성 — 다중행은 프로시저로, 돈은 앱에서

주문 하나를 만들려면 헤더 · 상품 N줄 · 배송지 · 가격 재검증 · 재고 차감 · 이력 · 결재선 · 장바구니 정리까지 여러 테이블을 써야 한다. 라인마다 쿼리를 보내면 상품 수만큼 DB 왕복이 늘고, 트랜잭션이 길어져 커넥션을 오래 쥔다.\
그래서 주문(SO) 쪽 다중행 처리는 **주문 생성 프로시저 한 번 호출**로 묶고, 공급사 발주는 결제가 확정된 뒤 **발주 생성 프로시저**로 만든다. 돈을 다루는 여신 차감과 결제는 테스트 · 디버깅이 되는 **앱 계층**에 남겼다. 여신 경로는 이 셋이 한 트랜잭션이라, 어느 단계가 실패해도 주문 전체가 롤백된다(부분 주문이 남지 않는다).

<figure class="diagram"><img src="/content-assets/b2b/order-payment/diagram-3.light.svg" alt="주문 생성 — 다중행은 프로시저로, 돈은 앱에서 다이어그램" class="diagram-light" loading="lazy" decoding="async"><img src="/content-assets/b2b/order-payment/diagram-3.dark.svg" alt="주문 생성 — 다중행은 프로시저로, 돈은 앱에서 다이어그램" class="diagram-dark" loading="lazy" decoding="async"></figure>

991줄짜리 주문 생성 프로시저를 앱 코드로 옮긴 등가 구현(라인을 IN 절로 묶은 배치 구현)을 실제로 만들어 비교했다. 두 구현이 7개 테이블 45행을 똑같이 만드는지 먼저 확인한 뒤에만 숫자를 인정했다.

<div class="table-wrap">

| **주문 1건 · 장바구니 20라인** | **앱 레벨** | **프로시저**   |
| --------------------- | -------- | ---------- |
| DB 왕복                 | 30회      | **11회**    |
| 응답 시간 (왕복 지연 1ms 주입)  | 403 ms   | **276 ms** |

</div>

- 왕복은 MySQL 전역 카운터의 차이로 셌다(4회 반복 같은 값). 상품 30개 · 공급사 5개로 늘려도 30 대 11이었다 — 라인을 묶은 앱 구현도 왕복이 상수라 격차는 일정하다.
- 응답 시간은 TCP 프록시로 왕복 지연을 0 · 1 · 2 · 5ms 넣어 쟀다(단건 3회 중앙값이라 ±30ms). 지연 곡선의 기울기 11.0 ms/ms 가 카운터로 센 왕복 11회와 맞았다.
- 프로시저 DDL 은 Flyway 마이그레이션으로 버전을 관리해, 앱 코드와 같은 리뷰 · 롤백 흐름에 태웠다.

<div class="table-wrap">

| **고르지 않은 안**          | **이유**                                           |
| --------------------- | ------------------------------------------------ |
| JPA 트랜잭션만             | 상품 · 공급사 수에 비례한 왕복, 조회와 차감 사이의 경쟁(이중 차감)         |
| JPA 비관적 락 + 배치 INSERT | 락을 쥔 채 앱↔DB 를 오가는 만큼 잠금이 길어진다 — 여신 잠금에만 이 방식을 썼다 |
| Saga · 이벤트            | 결제가 실패할 때마다 보상 트랜잭션을 여럿 써야 해 운영 부담이 크다           |
| Outbox · 비동기          | 주문번호를 사용자에게 바로 돌려줘야 한다                           |
| Redis 분산 락            | 락 서버가 단일 장애점이고, 해제에 실패하면 교착 위험이 있다               |

</div>

## 여신 이중 차감 — 여신 행 하나에서 줄을 세운다

여신 잔액이 100만 원인 기업에서 80만 원짜리 주문 두 건이 동시에 들어온다. 잠금 없이 '조회 → 차감'을 하면 둘 다 100만 원을 읽고 각자 차감한다.

<figure class="diagram"><img src="/content-assets/b2b/order-payment/diagram-4.light.svg" alt="여신 이중 차감 — 여신 행 하나에서 줄을 세운다 다이어그램" class="diagram-light" loading="lazy" decoding="async"><img src="/content-assets/b2b/order-payment/diagram-4.dark.svg" alt="여신 이중 차감 — 여신 행 하나에서 줄을 세운다 다이어그램" class="diagram-dark" loading="lazy" decoding="async"></figure>

**고친 것** — 모든 여신 결제는 시작할 때 기업의 유효 여신 행 1건을 `FOR UPDATE` 로 잠근다. 예산을 쓰는 기업도 이 행을 먼저 잠그므로, 같은 기업의 동시 주문은 이 행 하나에서 줄을 선다. 잠그는 행이 하나라 교착 위험도 낮다. 차감 직전에 가용액을 다시 읽어 부족하면 예외로 막는다(최후 저지선). 재고는 주문 생성 프로시저 안에서 상품 행을 `FOR UPDATE` 로 잠근다.

<aside class="callout tone-evidence" data-icon="🧪">

**테스트 11/11** — 쿼리 계약 3 · 서비스 가드 5 · 결제 멱등성 3.\
그중 하나는 검증하다 찾은 결함이다. 화면이 보낸 여신 사용액이 서버가 계산한 남은 결제 금액과 같은지 맞춰 보는 대사가 없었다. 고치고 회귀 테스트로 고정했다(0원 · 적게 보낸 값은 차단, 금액 조회에 실패하면 막는 쪽으로).

</aside>

## 결제 두 갈래 — PG · 여신/예산

<figure class="diagram"><img src="/content-assets/b2b/order-payment/diagram-5.light.svg" alt="결제 두 갈래 — PG · 여신/예산 다이어그램" class="diagram-light" loading="lazy" decoding="async"><img src="/content-assets/b2b/order-payment/diagram-5.dark.svg" alt="결제 두 갈래 — PG · 여신/예산 다이어그램" class="diagram-dark" loading="lazy" decoding="async"></figure>

- **PG** — 결제 행이 이미 '승인 완료'면 기존 결과를 그대로 돌려주고, '결제 대기'일 때만 PG 승인을 부른다. 상태로 지키는 멱등이라 이중 승인 · 이중 차감이 없다. 승인 뒤 다음 단계가 실패하면 PG 결제를 취소해 되돌린다(망취소). 결제 전에 페이지를 떠난 주문은 주문요청대기 상태로 두었다가 이탈 때 지워 고아 주문이 남지 않게 했다.
- **여신 · 예산** — 출처가 넷이다: 사용자 개인 예산 · 부서/조직 예산 · 계정조직 예산 · 기업 여신. 자동으로 넘기지 않고 권한 위계 순으로 보여 준 뒤 사용자가 고른다. 예산을 쓰는 기업은 예산이 필수이고, 아니면 기업 여신에서 바로 차감한다.\
  네 단계는 조직의 결정 권한과 맞춘 것이다. 셋으로 합치면 사업부장이 부서별 예산을 통제하지 못해 부서별 사용 내역을 추적할 수 없고, 다섯 단계가 필요한 고객사는 없었다.

## 결과 — 동시 120건, 초과 차감 0건

'여신 행 하나에서 줄을 세운다'는 주장은 단위 테스트로는 증명되지 않는다. 그래서 사용자 120명이 각자 장바구니(20개 × 9,900원 = 198,000원)로 **동시에 120건** 주문하게 하고, 여신(한도 1,000,000원)은 한 기업 것을 같이 쓰게 했다. 모든 요청이 같은 여신 행을 두고 다퉈야 잠금이 시험받는다. 기대는 5건만 성공이고, 판정은 k6 응답이 아니라 DB 원장으로 했다.

<div class="table-wrap">

| **지표**        | <strong>첫 측정 (쿼리 가드 있음)</strong> | <strong>재측정 2026-08-30 (쿼리 가드 없음)</strong> |
| ------------- | -------------------------------- | ------------------------------------------ |
| 주문 성공         | **5건**                           | **5건**                                     |
| 여신 사용액        | **990,000원** (5 × 198,000)       | **990,000원**                               |
| 최종 잔액         | **10,000원**                      | **10,000원**                                |
| 여신 부족 거절      | 101건                             | 72건                                        |
| 기타 거절 (그중 교착) | 14건 (10) — 로컬 패치 적용분             | 43건 (38) — 리포 상태                           |
| 5xx           | 0건                               | 0건                                         |

</div>

차감액이 성공 건수와 원 단위까지 맞았다. 같은 실험을 서로 다른 세 시점의 코드에서 반복해 모두 같은 결과였다.\
2026-08-21 에 쿼리 쪽 조건부 UPDATE 가드가 빠졌다. 누적 카운터를 기준으로 삼아, 취소 · 미정산이 쌓이면 실제 가용액과 어긋나 판정 근거가 될 수 없었기 때문이다(교체 작업은 내 범위 밖이었다). 그 뒤로 방어는 잠금과 차감 직전 재확인 두 층이라, 같은 실험을 다시 쟀고 결과는 같았다.\
기타 거절은 대부분 교착이었다. 이 교착은 원인을 찾아 고쳤다 — 「동시 주문 데드락 — 원인 규명과 처방」 카드. 교착으로 롤백된 주문은 여신 차감까지 되돌아갔다. 앱 로그에서 가용액이 10,000원(5건 차감)까지 내려갔다가 208,000원(4건)으로 돌아온 회차가 있었고, 그 주문 행도 남지 않았다. <strong>교착이 나도 돈은 새지 않았다.</strong>
