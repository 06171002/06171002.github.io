## 개요

B2B 구매 전체 프로세스를 담당하는 핵심 기능. 장바구니 → 주문(SO) → 공급사별 발주(PO) → 결제(PG/여신) → 배송까지의 흐름을 **SO/PO 이중 구조**로 설계했다.

하나의 주문에 여러 공급사 상품이 포함될 수 있으므로, 공급사별 배송·정산을 독립적으로 관리한다.

<div class="table-wrap">

| **SO/PO 이중 구조** | **결제 이중 경로** | **13개 주문 상태**        | **다중행 INSERT→1 CALL**    | **동시 이중차감 원천 차단**     |
| --------------- | ------------ | -------------------- | ------------------------ | --------------------- |
| 공급사별 독립 배송·정산   | PG + 여신·예산   | SO 13개 + 발주 라인 독립 상태 | 주문 생성(SO)·발주 생성(PO) 프로시저 | 여신·재고 FOR UPDATE 행 잠금 |

</div>

## 왜 이 설계가 필요했는가 (Problem)

B2B 전용몰에서 마주친 3가지 핵심 난제 — 단일 SO 모델·애플리케이션 레벨 트랜잭션으로는 해결 불가능했다.

<aside class="callout tone-scenario" data-icon="🎯">

**시나리오 1 — 부분 출고·부분 취소 정산**\
사용자가 공급사 A·B·C의 상품을 한 주문으로 구매. A는 출고 완료, B는 재고부족으로 취소, C는 처리중.\
→ 단일 주문 모델로는 "이 주문의 상태는 무엇인가?" 라는 질문에 답할 수 없다. 공급사별 분리 정산도 불가능.

</aside>

<aside class="callout tone-scenario" data-icon="⚡">

<strong>시나리오 2 — 여신 이중 차감 (동시성 위기)</strong>\
기업 여신 잔액 100만원. 동시에 2건의 주문(각 80만원)이 들어오는 상황.\
→ JPA `@Transactional` 만으로는 조회와 차감 사이 race condition 발생. 결과: 160만원 사용했지만 잔액 20만원 기록 → **60만원 초과 차감**.

</aside>

<aside class="callout tone-scenario" data-icon="🔥">

**시나리오 3 — 긴 트랜잭션 → 커넥션 풀 고갈**\
주문 1건 = 상품 N개 라인별 INSERT + 재고 차감 + 장바구니 정리 + 공급사별 PO = **상품 수에 비례한 수십\~100여 회 DB 라운드트립**.\
→ 동시 사용자가 늘면 커넥션 점유 시간 누적 → 신규 요청 타임아웃 위험.

</aside>

이 3가지를 동시에 해결하기 위해 <strong>SO/PO 이중 구조 + DB 프로시저 +</strong> `SELECT FOR UPDATE` **행 잠금** 의 조합으로 결정했다.

## 테이블 설계 — SO/PO 이중 구조

<aside class="callout tone-blue" data-icon="💡">

<strong>왜 SO/PO를 분리했는가?</strong>\
B2B 전용몰에서 하나의 주문(SO)에 여러 공급사의 상품이 포함된다. 공급사별로 **배송 추적·입고 확인·취소 처리·정산**을 독립적으로 관리해야 하므로, 고객 주문(Sales Order)과 공급사 발주(Purchase Order)를 분리했다.

</aside>

### 검토했던 대안들 (Analyze)

| **대안**                    | **장점**                                      | **단점**                                                           | **선택**                                |
| ------------------------- | ------------------------------------------- | ---------------------------------------------------------------- | ------------------------------------- |
| 1. 단일 SO + 공급사 항목 JSON 컬럼 | 스키마 단순, 단일 row로 주문 파악                       | 공급사별 상태 변경 시 전체 row UPDATE → 동시성 충돌. JSON 인덱스 활용 한계로 공급사별 조회 비효율 | ❌ 기각                                  |

</div>

## 핵심 설계 결정

### 1. 주문 생성 프로시저 — 트랜잭션 정합성 + 동시성 제어

<aside class="callout tone-orange" data-icon="⚙️">

주문 생성의 **SO측 다중행 처리**(주문 헤더 + 상품 N개 라인 + 배송지 스냅샷 + 가격 재검증 + 재고 차감 + 이력 + 결재선 연결 + 장바구니 정리)를 **주문 생성 프로시저 1회 CALL**로 원자화했다.

- **왕복 실측** — 앱 레벨 등가 구현을 실제로 만들어 A/B 비교했다. 주문 1건(장바구니 20라인) 기준 **프로시저 11회 vs 앱 레벨 30회**
- **응답시간** — 운영급 왕복 지연(1ms) 주입 시 **276ms vs 403ms**

**단, 여신 차감 · PO 생성 · 결제는 프로시저가 아니라 Spring** `@Transactional` **서비스 계층에서 오케스트레이션한다**

- **돈을 다루는 로직** — 테스트·디버깅이 가능한 앱 레이어에 둔다
- <strong>공급사 발주(PO)</strong> — 결제 확정 후 **발주 생성 프로시저**로 분리 생성한다 (하이브리드 트랜잭션 설계 — 아래)

</aside>

### 검토했던 6가지 대안 (Analyze)

"여러 테이블 동시 INSERT + 여신 차감"의 트랜잭션 정합성과 동시성을 보장할 6가지 방법을 비교했다.

<div class="table-wrap">

| **대안**                                                      | **장점**                                                     | **기각 사유**                                                                          |
| ----------------------------------------------------------- | ---------------------------------------------------------- | ---------------------------------------------------------------------------------- |
| 1. JPA + `@Transactional` (순수)                              | 구현 단순, 모든 로직 Java 코드                                       | 상품·공급사 수에 비례한 다수 RT, 조회→차감 사이 race condition (이중 차감 위험)                            |
| 2. JPA + 비관적 락(`@Lock(PESSIMISTIC_WRITE)`) + JDBC 배치 INSERT | Java 코드 유지하며 동시성·RT 동시 개선 — 락으로 이중 차감 차단, 배치로 INSERT 왕복 축소 | 배치로도 RT 잔존(다중 statement·flush), **락 보유 구간이 앱↔DB 왕복만큼 길어져** 동시 처리량 저하. 로직이 앱·DB로 분산 |
| 3. Saga 패턴 + 이벤트                                            | 마이크로서비스 확장성, 부분 실패 복구                                      | 결제 실패 시 보상 트랜잭션 N개 작성 → 운영 복잡도 ↑↑. 현 인력으로 운영 부담                                    |
| 4. Outbox 패턴 + 비동기 처리                                       | 최종 일관성 보장, 메시지 신뢰성                                         | 주문번호를 사용자에게 동기 응답해야 함 → 비동기 부적합                                                    |
| 5. Redis 분산 락 + 애플리케이션                                      | JPA 유지하면서 동시성 제어                                           | 락 획득/해제 비용, Redis 단일 SPOF, 락 해제 실패 시 데드락 위험                                        |
| 6. DB 프로시저 + `SELECT FOR UPDATE`                            | 1회 RT, 행 잠금으로 race condition 원천 차단, 단일 DB 트랜잭션             | DB 종속성, 디버깅 난이도 ↑ (Flyway 형상관리로 완화 — 아래 참고)                                        |

</div>

<aside class="callout tone-green" data-icon="✅">

**선택: SO 생성은 6번(프로시저) + 여신 동시성은 2번(앱 비관적 락) — 하이브리드**

- **다중행 SO/PO INSERT** — 상품·공급사 수만큼 반복 → 주문 생성·발주 생성 프로시저로 라운드트립 압축
- **여신 차감의 동시성** — 앱 레이어에서 기업 여신 행을 `SELECT FOR UPDATE`로 잠그고, 잠금 구간 안에서 실효 산식 재계산값을 반영

→ 돈을 다루는 로직은 앱에 두어 테스트·디버깅을 확보하고, 대량 INSERT만 DB로 내려 네트워크 비용을 줄인 **의도적 분리**다.\
프로시저의 DB 종속성·버전관리는 Flyway로 완화(아래).

</aside>

<aside class="callout tone-green" data-icon="🛡️">

**프로시저의 약점(테스트·버전관리)을 어떻게 보완했나**

- **형상관리** — 프로시저 DDL을 **Flyway 마이그레이션**으로 버전 관리 → 변경 이력·코드리뷰·롤백을 애플리케이션 코드와 동일한 파이프라인으로 추적해 *DB에 로직을 두는 안티패턴 우려*를 상쇄
- **테스트·추적성** — 프로시저는 OUT 결과코드(`00000`/실패코드)로 성공/실패를 앱에 전달해 단언·로깅 가능

단, 슬라이스 테스트가 H2 기반이라 MySQL 프로시저 자체 검증은 실 MySQL 통합 환경이 필요하다.

</aside>

### 비교: 애플리케이션 레벨 vs DB 프로시저

#### ❌ 애플리케이션 레벨로 구현했다면

주문 생성 시 상품 N개, 공급사 M개 기준으로 **다수의 독립 쿼리**가 발생한다.

```text
// 애플리케이션 레벨 구현(가정) — 라인마다 쿼리를 반복하면
장바구니 조회  // 1회
주문 헤더 저장 + 주문번호 채번  // 2회
for 장바구니 라인: 주문 라인 저장  // N회
for 공급사: 발주 저장, for 라인: 발주 라인 저장  // M + N회
결제 저장  // 1회
if 여신 결제: 여신 조회 + 차감  // 2~3회
for 장바구니 라인: 장바구니 삭제  // N회
// 골격만도 3N + 2M + 6 ≈ 42회 (상품 10 · 공급사 3). 라인별 가격 재검증 · 재고 잠금까지 넣으면 더 많다
```

<aside class="callout tone-red" data-icon="⚠️">

**문제점 1 — 네트워크 비용**: 상품 10개, 공급사 3개 기준 **수십\~100여 회 네트워크 라운드트립** 발생.

- **라운드트립마다 반복** — 각 쿼리마다 SQL 파싱 → 실행 → 결과 직렬화 → 네트워크 전송 → 역직렬화
- **오버헤드 가중** — INSERT가 대부분이므로 JPA flush + 개별 시퀀스 채번 오버헤드까지 추가

→ 트랜잭션이 길어지면서 DB 커넥션을 오래 점유 → 동시 사용자 증가 시 **커넥션 풀 고갈 위험**.

</aside>

<aside class="callout tone-red" data-icon="⚠️">

**문제점 2 — 여신 이중 차감**: 여신 잔액 100만원인 상황에서 동시에 2건의 주문(각 80만원)이 들어오면 —\
① 트랜잭션 A가 여신 조회(100만원)\
② 트랜잭션 B도 여신 조회(100만원)\
③ A가 차감(100→20)\
④ B도 차감(100→20)\
→ 결과적으로 160만원을 사용했지만 잔액은 20만원으로 기록되어 **60만원 초과 차감**이 발생한다.\
애플리케이션 레벨에서는 조회→차감 사이 다수 쿼리 실행 시간만큼 **경쟁 윈도우가 넓어져** 이 위험이 커진다.

</aside>

#### ✅ DB 프로시저로 구현한 결과

**주문 생성 프로시저 1회 CALL**로 SO측 다중행(헤더 + 라인 N + 배송지 + 이력 + 장바구니 정리)을 원자적으로 처리한다. 여신 차감·PO·결제는 포함하지 않는다(앱 계층·발주 생성 프로시저 담당).

```text
-- 주문 생성 프로시저 — SO 쪽 다중행 처리만 1 CALL 로
BEGIN
    -- 1. 정합성 검증 (배송지 · 결제수단 · 주문불가 상품)
    -- 2. 주문 헤더 INSERT (주문요청대기 재사용 또는 신규) + 주문번호 채번
    -- 3. 배송지 스냅샷 INSERT
    -- 4. 커서로 장바구니 라인 순회: 상품 SELECT ... FOR UPDATE (재고) → 카트가 vs 현재가 재검증 → 주문 라인 INSERT → 재고 차감
    -- 5. 헤더 금액 집계 + 이력 + (결재선) + 장바구니 정리
END;
-- 여신 차감 · PO · 결제는 하지 않는다 (Spring @Transactional 서비스가 담당)
```

<aside class="callout tone-green" data-icon="✅">

**핵심**

- <strong>재고(프로시저)</strong> — 주문 생성 프로시저 내부의 `SELECT ... FOR UPDATE`는 **재고** 행 잠금이다(상품별 재고 이중 차감 차단) + 카트가↔현재가 재검증
- <strong>여신(앱)</strong> — **여신** 이중 차감 차단은 별개로, 앱 계층의 여신 결제 처리가 기업 여신 행을 `SELECT FOR UPDATE`로 잠그고, 차감 직전 실효 가용액을 재조회해 부족하면 예외로 차단한다

→ 동시성 안전은 <strong>재고(프로시저)·여신(앱)</strong> 두 지점의 행 잠금으로 보장된다.

</aside>

### 2. 스냅샷 전략 — 3개 원본 → 3개 대상 복사

이후 상품 가격·사용자 정보가 변경되어도 기존 주문에 영향 **0건** — 가격 변동에 의한 정산 분쟁을 원천 차단한다.

### 4. 결제 이중 경로

<figure class="diagram"><img src="/content-assets/b2b/order-payment/diagram-4.light.svg" alt="4. 결제 이중 경로 다이어그램" class="diagram-light" loading="lazy" decoding="async"><img src="/content-assets/b2b/order-payment/diagram-4.dark.svg" alt="" class="diagram-dark" loading="lazy" decoding="async" aria-hidden="true"></figure>

- **PG 결제**: PG 결제창 → 승인 → 결제 키로 서버 확인(결제 승인 API) → **발주 생성**
- **여신/예산**: 앱 계층에서 기업 여신 행 `FOR UPDATE` 잠금 + 차감 → **발주 생성** → 즉시 완료
- 여신/예산 **4단계 출처**(사용자·조직·계정조직 예산 + 기업 여신): 자동 폴백이 아니라 **권한 위계 순으로 제시 → 사용자 선택**. 예산사용 기업은 예산 필수, 비예산 기업은 기업 여신 직접 차감

<aside class="callout tone-orange" data-icon="🤔">

<strong>왜 4단계인가? (Analyze)</strong>\
**조직 의사결정 권한 위계와 일치**시키기 위함. 각 단계는 서로 다른 통제 권한을 가진다.

**1. 사용자 개인 예산** — 소액 자율 결제 (영업사원 출장비 등)\
**2. 부서/조직 예산** — 팀장 통제 (팀 단위 회식·소모품)\
**3. 계정조직 예산** — 사업부장 통제 (사업부 단위 정기 구매)\
**4. 기업 여신** — 사후 정산, 신용 한도 (대규모 발주)

**3단계로 줄였을 때**: 부서 예산과 사업부 예산을 합치면 사업부장이 부서별 예산을 통제 못함 → 각 부서 사용 내역 추적 불가능.\
**5단계 추가**: 현 고객사 표본 기준 권한 위계가 5단으로 가는 케이스 없음. 도메인 over-engineering.

</aside>

### 5. 결제 멱등성 — 중복 승인 차단

<aside class="callout tone-blue" data-icon="🔁">

**PG 결제 승인 중복 호출 방어**\
PG 웹훅 재전송·사용자 새로고침으로 결제 승인 요청이 2회 들어올 수 있다.\
결제 행을 조회해 **이미 승인 완료 상태면 기존 결과를 그대로 반환**(no-op)하고, 결제 대기 상태일 때만 PG 승인 API를 호출하는 **상태 가드**로 멱등성을 보장한다.\
→ **이중 승인·이중 차감 차단**. (참고: PG 결제 키 자체에는 UNIQUE 제약이 없다 — 상태 기반 멱등)

</aside>

### 6. 실패·보상 처리

<aside class="callout tone-gray" data-icon="↩️">

**① 동기 결제 경로(여신) — 단일 트랜잭션**\
주문 생성 서비스는 주문 생성 프로시저 → 여신 차감 → 발주 생성 프로시저까지 하나의 Spring `@Transactional` 안에서 실행되므로 어느 단계 실패든 **전체 롤백**(주문 헤더·라인 포함, 부분 주문 없음).\
프로시저는 `SIGNAL SQLSTATE '45000'` + OUT 결과코드로 실패를 전달하고, 앱이 업무 예외로 던져 롤백을 유발한다.

**② PG 경로 — 두 트랜잭션**\
주문 생성과 결제 승인이 분리되므로, 승인은 멱등(§5)으로 · 결제 전 이탈은 주문요청대기 + 페이지 이탈 Beacon 삭제로 고아 주문을 막는다.

</aside>

### 7. 여신 동시성 — 단일 직렬화 지점

<aside class="callout tone-orange" data-icon="🔒">

모든 여신 결제는 처리 시작 시 **기업의 유효 여신 행 1건을** `FOR UPDATE`<strong>로 잠근다.</strong>

- **직렬화** — 예산 사용 기업이든 아니든 이 행을 먼저 잠그므로, 같은 기업의 동시 여신 주문은 이 한 행에서 **직렬화**된다
- **추가 가드** — 차감 직전 재조회에서 가용액이 부족으로 바뀌면 **최후 저지선이 예외로 차단**한다 (서비스 계층)

→ 다중 행 락이 아닌 **단일 행 직렬화**라 데드락 위험도 낮다.

⚠️ **2026-08-21 변경** — 종전엔 매퍼 계층에도 '가용액 ≥ 사용액' **조건부 UPDATE** 가드가 있었으나, 이 가드는 **raw 카운터**를 기준으로 삼는데, 취소·미정산이 누적되면 raw 와 실효 가용액이 어긋나므로 판정 근거로 쓸 수 없다. 현재는 잠금 구간에서 실효 산식 재계산값을 절대 SET 하고, 방어는 **① FOR UPDATE 직렬화 + ② 서비스 최후 저지선** 2층이다. <em>(교체 작업은 본인 범위 밖)</em>

</aside>

<aside class="callout tone-evidence" data-icon="🧪">

**테스트 검증** — 여신 차감 2중 안전망(§7) + 결제 멱등성(§5) + 금액 대사, 3계층 · **11/11 통과** (2026-08-21 매퍼 계약 변경 반영)

- **쿼리 계약** (슬라이스 @MybatisTest·H2) 3/3: **절대 SET 계약** — raw 카운터 현재값과 무관하게 넘긴 값으로 덮어쓴다. 가용액 판정은 쿼리가 아니라 **서비스 계층이 책임진다**는 것을 계약으로 명시했다 / 삭제된 여신 행에는 반영되지 않는다
- **서비스 가드** (단위 Mockito) 5/5: ① 실효 가용액 부족 → 1차 게이트 차단(결제행·UPDATE 미시도) ② **사전 검증 통과 후 동시 경합으로 갱신이 0행이면 최후 저지선이 예외로 차단**(레이스 방어 — 여신 스냅샷 미진행·롤백) ③ **금액 대사** — 클라이언트가 보낸 여신 사용액이 서버가 계산한 잔여 결제금액과 다르면 차단(0원·과소 차단 / 요약 조회 실패 시 fail-closed) — 대사 부재 결함을 검증 중 발견·수정한 회귀 고정
- **멱등성** (기존 회귀) 3/3: 승인 완료 상태의 중복 호출은 PG 미호출 no-op + 승인 후 후속 실패 시 망취소 보상

⚠ 단, 실제 동시 120건 요청에서의 직렬화·이중차감 0건은 단위/슬라이스로 증명 불가 — 위 "재현 가능한 측정 시나리오"의 부하테스트 몫.

</aside>

| 기대값    | `floor(1,000,000 ÷ 198,000)` = **5건만 성공** |
| 데이터    | 사용자 120명이 각자 장바구니 — **단, 여신은 기업 단위로 공유**  |
| 판정     | k6 응답이 아니라 **DB 원장**(기업 여신 테이블)으로 검증      |

</div>

<aside class="callout tone-evidence" data-icon="🧪">

**사용자는 분리하되 여신은 공유시킨 이유** — 모든 요청이 **같은 여신 행 하나**를 두고 다퉈야 `FOR UPDATE` 가드가 시험받는다. 장바구니 측정과는 정반대 설계로, 여기서는 경합이 실험의 본질이다.

</aside>

### 부하 중 발견한 실제 결함 — 동시 주문 데드락

<aside class="callout tone-blue" data-icon="🔒">

<strong>부하 테스트에서 동시 주문 데드락을 발견했다.</strong> 정합성은 지켜졌지만(초과차감 0건) 120건 중 일부가 `Deadlock found when trying to get lock` 으로 실패했고, `SHOW ENGINE INNODB STATUS` 의 LATEST DETECTED DEADLOCK 기록을 직접 읽어 원인을 확정했다.

조사가 커져 원인 규명과 수정은 「동시 주문 데드락」 카드로 옮겼다.

</aside>

핵심만 요약하면 — 이 부하에서 난 교착의 원인은 **① 상품 ↔ 채번 카운터 잠금 순서 역전**, **② 주문번호 임시값 'TEMP' 의 유니크 인덱스 충돌**, **③ 채번 루틴 내부의 S→X 승격** 세 가지다. 메커니즘이 서로 달라 <strong>하나만 고치면 개선이 안 나거나 교착이 다른 자원으로 옮겨간다.</strong>

<aside class="callout tone-orange" data-icon="🔍">

**원인 규명 방법** — 추측을 두 번 했고 둘 다 틀렸다("커서에 ORDER BY 없음", "사용자별 상품 잠금 순서 상이"). 실제 원인은 `SHOW ENGINE INNODB STATUS` 의 **LATEST DETECTED DEADLOCK 기록**을 직접 읽어서 확정했다.

또 하나 — 두 번째 가설의 <strong>기각 자체도 나중에 틀렸다는 것을 알았다.</strong> "전원 동일 순서"는 시스템의 성질이 아니라 부하 시드의 성질이었다.

</aside>

<aside class="callout tone-green" data-icon="✅">

<strong>이후 모두 수정·검증을 마쳤다.</strong> 세 원인을 고친 뒤에도 다른 경로의 교착(결재 승인 · 상품 간 잠금 순서 · 취소)이 남아 있었고, 그것까지 고쳐 로컬 재현과 부하 테스트로 교착 0건을 확인했다 — 「동시 주문 데드락」 카드 참조.

</aside>

### 부수 확인 — §6 실패·보상 처리가 실증되었다

<aside class="callout tone-green" data-icon="↩️">

데드락으로 죽은 트랜잭션은 **여신 차감까지 정상 롤백**되었다.\
앱 로그상 가용액이 한때 10,000원(= 5건 차감)까지 내려갔다가 최종 208,000원(= 4건)으로 복구된 회차가 있었고, 그 주문 행도 남지 않았다.\
→ <strong>데드락이 나도 돈은 새지 않는다.</strong> §6 이 주장한 원자성이 의도치 않게 실측으로 증명된 셈이다.

</aside>

### 이 측정이 말하지 않는 것

<aside class="callout tone-gray" data-icon="📐">

- **운영 환경이 아니다** — 로컬 단일 인스턴스·컨테이너 MySQL. 교착 수치는 이 환경의 값이며 운영 수치가 아니다.
- **동시 부하 구간은 재지 않았다** — 왕복·응답시간 A/B 는 단건 기준이다. 주문은 장바구니를 소비해 시드 사용자 120명으로는 반복 부하를 걸 수 없었다.
- **예산 결제 경로는 측정하지 않았다** — 여신 직접 결제(예산 배정 없음) 경로만 검증했다.
- ✅ <strong>현재 차감 경로에서 재측정 완료 (2026-08-30)</strong> — 위 「재측정」 절 참조. 매퍼 조건부 UPDATE 가 사라진 뒤에도 초과차감은 0건이었다.

</aside>
