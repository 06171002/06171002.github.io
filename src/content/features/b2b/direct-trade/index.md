## 개요

구매기업이 공급사와 **직접 거래**하는 트랙을, **이미 운영 중이던 대행(agency) 트랙 위에** 얹은 기능. 신규 개발이 아니라 돌아가는 파이프라인에 대한 개조였다. 운영사가 거래 당사자에서 빠지므로, 판정 → 장바구니 → 주문 → 정산 → 클레임 → 통계까지 **전 계층에서 운영사를 걷어내야** 한다.

<div class="table-wrap">

| **2축 판정**       | **판정 3값**         | **운영사 API 0개**     | **잔차 0 청구 축** | **200개 테스트**     |
| --------------- | ----------------- | ------------------ | ------------- | ---------------- |
| 고객사 연결 × 품목 소유자 | 직거래 / 대행 / **차단** | 격리를 필터가 아닌 **부재**로 | 라인합계를 그대로 청구  | 31개 파일 (단위·슬라이스) |

</div>

## 왜 이 설계가 필요했는가 (Problem)

<aside class="callout tone-scenario" data-icon="🎯">

**시나리오 1 — 직거래는 상품의 속성이 아니다**\
같은 상품이라도 **A기업에겐 직거래, B기업에겐 대행**이다. 표준품목의 소유자가 고객사인지 운영사인지, 그리고 그 고객사와 연결이 있는지에 따라 갈린다.\
개발 데이터에서도 한 품목이 **1개 기업에는 고객사 소유 · 51개 기업에는 운영사 소유**였다.\
→ 상품 테이블에 플래그 하나 박는 설계로는 **표현 자체가 불가능**하다.

</aside>

<aside class="callout tone-scenario" data-icon="🚫">

**시나리오 2 — 조용한 대행 폴백은 사고다**\
품목 소유자는 고객사인데 그 고객사와 **연결이 없는** 경우가 있다.\
여기서 "판정 실패 → 일단 대행"으로 폴백하면, 운영사가 **당사자가 아닌 거래를 자기 매출로 떠안는다**.\
→ 폴백이 아니라 <strong>차단(주문 불가)</strong> 이라는 제3의 값이 필요하다.

</aside>

<aside class="callout tone-scenario" data-icon="🧬">

**시나리오 3 — 한 주문에 두 트랙이 섞이면 안 된다**\
결제 수단·정산 주체·격리 범위가 **전부 문서(SO) 단위**다. 대행 라인과 직거래 라인이 한 주문에 섞이면 이 세 가지가 동시에 정의 불능이 된다.\
→ 주문 생성 시점 검증만으로는 늦다. **장바구니 선택 단계부터** 막아야 한다.

</aside>

<aside class="callout tone-scenario" data-icon="🔒">

**시나리오 4 — 운영사 격리의 진입점이 수십 곳이다**\
관리자 주문목록·카운트·요약·엑셀, 매출/매입 정산 5지점, 통계 적재 5문, 클레임 환불, 상품 카탈로그 …\
**하나만 새도** 운영사가 당사자 아닌 거래를 열람하게 된다. 그리고 새 진입점은 계속 추가된다.

</aside>

<aside class="callout tone-scenario" data-icon="💰">

**시나리오 5 — 공급사 청구액에 1원이 남는다**\
직거래는 운영사 마진이 없으므로 **공급사 청구액 == 구매사 결제액**이어야 한다.\
그런데 공급가를 *개당 단가 × 수량* 으로 되짚으면 나누어떨어지지 않을 때 **잔차 1원**이 남는다.\
→ 전량 취소해도 최종 청구액이 0이 되지 않는다.

</aside>

## 검토했던 판정 축 (Analyze)

"이 주문이 직거래인가"를 무엇으로 판정할지 — 이 선택이 나머지 전부를 결정했다.

<div class="table-wrap">

| **대안**                                        | **장점**                            | **기각 사유**                              | **선택**                                |
| --------------------------------------------- | --------------------------------- | -------------------------------------- | ------------------------------------- |
| 1. 상품 테이블에 직거래 여부 컬럼                          | 조회 단순, 인덱스 1개면 끝                  | 같은 상품이 기업마다 다른 트랙이다 — **표현 불능**        | ❌                                     |
| 2. 공급사 단위 플래그                                 | 쌍 단위라 관리 지점이 적음                   | 같은 공급사도 **품목별로** 소유자가 갈린다              | ❌                                     |
| 3. 주문 시점에 사용자가 선택                             | 구현 최단, 판정 로직 불필요                  | 오지정 한 번에 **정산 축이 통째로 틀어지고** 사후 감사가 불가능 | ❌                                     |
| 4. <strong>(고객사 연결 × 표준품목 소유자) 2축 판정</strong> | 기업별·품목별 차이를 정확히 표현, 원자료가 남아 감사 가능 | 조인 깊이 증가 · 목록 판정 시 N+1 위험              | <span class="chosen-mark">✅</span> 선택 |

</div>

<aside class="callout tone-green" data-icon="✅">

**선택: 4번 — 다만 판정 결과는 2값이 아니라 3값**\
**직거래**(고객사 소유 + 연결 있음) / **대행**(운영사 소유) / **차단**(고객사 소유 + 연결 없음).\
세 번째 값이 시나리오 2 의 조용한 폴백을 구조적으로 차단한다.\
N+1 위험은 **목록 판정을 쿼리 1회로 고정**해 해소했다 (테스트로 잠금).

</aside>

## 핵심 설계 결정

### 1. 2축 판정 — 6개 조건이 전부 AND

<aside class="callout tone-orange" data-icon="⚖️">

자격이 서려면 다음이 **모두** 참이어야 한다.\
① 연결된 고객사가 그 표준품목을 **고객사 소유**로 갖고 있음 · ② 소유 고객사와 **나의** 연결이 존재 · ③ 소유행이 사용 중 · ④ 소유행이 삭제되지 않음 · ⑤ 연결이 사용 중 · ⑥ 연결이 삭제되지 않음 · 그리고 표준품목이 살아 있을 것.

하나라도 흘리면 **남의 고객사 소유로 내 상품이 자동승인**되거나, **끊은 직거래로 자동승인이 계속된다**.

</aside>

> 6개 조건은 어느 하나만 흘려도 **판정이 반대로 뒤집힌다**. 그래서 AND 묶음을 한 번에 검증하지 않고, 조건별로 쪼개 각각 독립 테스트로 고정했다.

### 2. 트랙 순도 — 2단 가드

<aside class="callout tone-evidence" data-icon="🧪">

**① 장바구니 선택 시** — 대행 + 직거래가 함께 선택되면 거부하고 선택 상태를 저장하지 않는다. 차단은 직거래 쪽으로 묶어 대행과 섞이는 것을 막는다.\
**② 주문 생성 시** — 다시 판정해 동질성을 검증하고 주문 헤더에 직거래 여부 스냅샷을 박는다. 혼합·차단 단독 모두 거부.

선택 **해제**는 검사하지 않는다 — 내리는 동작은 혼합을 만들 수 없다.

</aside>

### 3. 격리는 조인이 아니라 스냅샷 등호

<aside class="callout tone-purple" data-icon="🔐">

격리 판정을 매번 조인으로 역산하지 않고, **주문 헤더의 직거래 여부 스냅샷을 정본**으로 삼는다.

- 혼합이 금지(§2)이므로 헤더 플래그 하나로 **라인 전체가 직거래임이 보장**된다
- 클레임 병합 집계도 **주문 헤더 조인으로 트랙을 판정** — 라인 축 판정은 금지
- 관리자 주문 목록·카운트·요약·엑셀 **네 경로 전부**에서 동일하게 배제

→ 조인 기반이면 연결이 나중에 끊겼을 때 **과거 주문의 트랙이 소급 변경**된다. 스냅샷은 그것을 막는다.

</aside>

### 4. 운영사용 직거래 API 를 **0개**로 둔 것

<aside class="callout tone-gray" data-icon="🚪">

직거래 전용 관리자 API 를 <strong>의도적으로 만들지 않았다.</strong> 운영사는 당사자가 아니기 때문이다.\
대신 기존 관리자 진입점마다 배제 필터를 실었고, 발주 상세는 직거래 라인이 섞이면 403 이 아니라 **404** 를 반환한다 — **존재 자체를 누설하지 않기** 위해서다.\
주문·발주·배송 **세 축 전부**에 같은 가드를 걸었다.

</aside>

### 5. 공급사 청구 축 = 라인합계 (개당 축 금지)

<aside class="callout tone-green" data-icon="💵">

공급가를 개당 단가로 되짚지 않고 **라인합계를 그대로** 청구 축으로 쓴다.

- 나누어떨어질 때 — 공급가액 + 세액 == 구매사 결제액 (정확 일치)
- 나누어떨어지지 않을 때 — **잔차 0** (개당 축으로 되돌리면 +1원이 남는다)
- 전량 취소 시 최종 청구액이 **정확히 0**

SQL 자체에 직거래 여부 게이트를 두어 **대행 주문에는 닿지 않는다** (fail-closed).

</aside>

### 6. 연결·초대 생명주기

<div class="table-wrap">

| **상황**              | **처리**                            |
| ------------------- | --------------------------------- |
| 사업자번호 일치 공급사 **1곳** | 연결요청 + 사업자번호 스냅샷                  |
| **복수** 공급사와 일치      | 임의 선택하지 않고 **초대**로 전환 — 오연결 방지    |
| **미가입** 사업자번호       | 초대 + 토큰 발급 → 가입 후 **이메일 매칭**으로 소진 |
| 연결 **해제**           | 행을 지우지 않고 사용 여부만 끈다 (다른 출처 행은 불변) |
| **재연결**             | 해제된 직거래 행을 다시 켠다 — 새 행을 만들지 않음    |
| 승인 시 수동 등록 행이 이미 있음 | 출처를 직거래로 **승격** (목록·해제 토글 정합)     |

</div>

<aside class="callout tone-gray" data-icon="🛡️">

**링크 유출 방어** — 초대 토큰은 **초대받은 이메일 계정으로만** 수락 가능하다(대소문자 무시). 다른 계정·자사 발송분은 거절. 만료 토큰은 상태·토큰을 **무변경**으로 두고 400.\
**종사업장 차단** — 연결은 모기업 단위라 종사업장 계정의 요청·수락을 모두 막는다.

</aside>

### 7. 예산 환원 — 직거래 원장만

<aside class="callout tone-orange" data-icon="↩️">

직거래 클레임 완료 시 PG 를 호출하지 않고 **예산 원장에 음수행을 넣어** 되돌린다.

- 원 사용행의 **배분정보·결제수단·참조번호를 그대로 복사**
- **순잔액을 상한**으로 복원 (원 차감액 초과 불가) · 순잔액 0이면 INSERT 하지 않음(멱등)
- 원장 행이 직거래 차감분이 **아니면 되돌리지 않는다** — 여신 원장 오복원 가드
- 부분취소 N차에서도 회차 합계가 원 차감액을 넘지 않는다

</aside>

## 설계가 만든 결과 (Result)

<aside class="callout tone-blue" data-icon="📊">

직거래는 **판정 하나가 틀리면 돈의 귀속이 바뀌는** 도메인이다. 그래서 설계 결정마다 불변식을 세우고 테스트로 고정했다.\
**31개 파일 · 200개 테스트** (단위 + `@MybatisTest` 슬라이스).

</aside>

### 회귀로 고정한 위험 지점

<aside class="callout tone-red" data-icon="🐛">

**① 비활성 소유행** — 소유행이 비활성인 경우는 6개 중 가장 빠뜨리기 쉽고, 빠지면 **이미 끊은 직거래가 계속 자동승인된다**. 그래서 6개 조건을 쪼개 각각 테스트로 잠갔다.

**② 정산 진입점 누락** — 배제 필터가 매출·매입 정산 진입 지점 **5곳 전부**에 실려 있는지를 별도 테스트로 센다. 진입점은 **수동으로 추가**되므로 누락이 구조적으로 반복될 수 있어서다.

**③ 알림 링크 404** — 승인·반려·해제 세 알림의 링크가 실제 화면 경로를 가리키는지, **하위 경로가 섞이지 않았는지**를 잠갔다.

**④ 무음 유실** — 상대 회사에 슈퍼관리자가 0명이면 회사 대표 이메일로 **폴백** 발송한다. 폴백도 없으면 경고 로그 후 종료 — 조용히 사라지지 않는다.

</aside>

### 동시성 결함 — 연결요청 중복 가드 (미수정)

<aside class="callout tone-red" data-icon="🔥">

<strong>부하 테스트가 실제 결함을 잡았다.</strong> 로컬 부하 하네스에서 같은 (구매기업 → 공급사) 쌍의 연결요청을 동시에 보내자, "같은 쌍의 대기 요청은 1건" 이라는 규칙을 깨고 <strong>대기 요청이 여러 건 생겼다.</strong>

</aside>

<aside class="callout tone-orange" data-icon="🔍">

**원인** — 누락이 아니라 **설계 선택의 미완성**이다. 재요청 이력을 남기려고 DB 유니크 제약을 일부러 두지 않고, "같은 쌍의 활성 요청 1건" 은 서비스 계층에서 검사하기로 했다. 그 판단은 합리적이지만, 검사와 삽입 사이를 잠그지 않았다(check-then-insert). 그래서 동시 요청들이 **아직 아무도 삽입하기 전에** 일제히 검사를 통과한다.

가드 자체는 정상이다 — 대부분의 요청은 걸렸고, 검사와 삽입 사이의 창으로 들어온 몇 건만 통과했다.

</aside>

<aside class="callout tone-blue" data-icon="🛠️">

<strong>수정 방향 (미적용)</strong> — 재요청 이력을 살리면서 활성 1건을 강제하려면 둘 중 하나다.\
① **부분 유니크** — 활성 상태일 때만 값이 채워지는 generated column 을 두고 (구매기업, 공급사, 그 컬럼)에 UNIQUE — 클레임 수거 중복 방지에 이미 쓰는 기법\
② **잠금 후 삽입** — 쌍 키를 잠그고 검사·삽입을 한 트랜잭션으로\
→ ① 이 이 도메인에 이미 있는 패턴과 일관된다.

</aside>

### 이 검증이 말하지 않는 것

<aside class="callout tone-gray" data-icon="📐">

- **연결요청 동시성 결함은 아직 고치지 않았다** (위 절). **해제·재연결 토글과 승인 멱등은 미측정**이다 — 공급사 쪽 서버를 이번 측정 환경에서 구동하지 못했다.
- **나머지 200개는 단위·슬라이스다** — 판정·순도·격리·정산 축은 부하로 재지 않았다.
- **격리는 열거 기반이라 구조적 한계가 남는다** — 진입점마다 필터를 다는 방식이라, <strong>새 진입점이 추가되면 다시 샌다.</strong> 정산 5지점 카운트 테스트가 그 방어책이지만 전 계층을 덮지는 못한다.
- **E2E 는 없다** — 초대 메일 수신 → 가입 → 매칭까지의 실제 왕복은 검증 범위 밖이다.

</aside>
