## 붙이기 전에 두 가지를 확인했다

엔진은 여러 쇼핑몰에 붙이려고 만들었다. 실제 쇼핑몰에 붙이기 전에 회사가 운영 중인 쇼핑몰 하나를 대상으로, 그 쇼핑몰의 쿠폰 · 포인트 계산을 엔진이 그대로 낼 수 있는지(**재현 테스트**), 그 쇼핑몰의 주문 · 취소 흐름에 엔진을 끼워도 끝까지 도는지(**시험 연결**)를 확인했다.

<div class="table-wrap">

| 미리 정한 것                                         | 까닭                                       |
| ----------------------------------------------- | ---------------------------------------- |
| 시험 연결은 로컬에서만 한다 — 공유 개발 DB 를 쓰지 않는다             | 공유 개발 DB 에 시험 주문을 남기지 않는다                |
| 쇼핑몰 쪽 코드는 따로 둔 작업 폴더에만 두고, 그 저장소에 커밋하지 않는다      | 그 쇼핑몰이 엔진을 쓰기로 한 것이 아니다                  |
| 주문 서비스를 통째로 띄우지 않고, 쿠폰 · 포인트에 닿는 단계만 같은 순서로 부른다 | 통째로 띄우려면 결재 · 예산 · 결제 대행 · 발주가 함께 있어야 한다 |

</div>

## 재현 테스트 — 같은 주문을 두 쪽에서 계산

쇼핑몰의 계산 규칙을 코드에서 읽어 테스트 전용 **참조 식**으로 옮기고, 같은 주문을 엔진으로 다시 계산했다. 기대값은 손으로 계산한 숫자와 참조 식을 **함께** 둔다 — 숫자만 두면 어떤 규칙에서 나왔는지 알 수 없고, 식만 두면 식이 틀려도 모른다. 결과가 다른 사례는 엔진을 고치지 않고 두 값을 모두 숫자로 테스트에 고정했다.

<figure class="diagram"><img src="/content-assets/coupon/replay-and-trial/diagram-2.light.svg" alt="재현 테스트 — 같은 주문을 두 쪽에서 계산 다이어그램" class="diagram-light" loading="lazy" decoding="async"><img src="/content-assets/coupon/replay-and-trial/diagram-2.dark.svg" alt="재현 테스트 — 같은 주문을 두 쪽에서 계산 다이어그램" class="diagram-dark" loading="lazy" decoding="async"></figure>

- **같다 9** — 정액 · 정률 · 최대 할인 · 최소 주문 금액 · 끝전 · 포인트 사용 단위 · 중복 규칙 · 기준 금액 · 포인트 두 종류 · 세 번 나눠 취소.
- **의도한 차이 6** — 설계할 때 일부러 다르게 정한 곳이다(계산 순서, 포인트를 나누는 기준 등). 차이가 정한 그대로 나오는지 숫자로 확인했다.
- **무작위 대조** — 무작위로 나눠 취소한 2,000건에서 클레임마다의 차이가 1원 이하이고, 합계는 언제나 같다.
- 끝전을 나누는 쪽의 차이는 코드를 읽는 것만으로는 확정할 수 없어, 쇼핑몰의 배분 식을 로컬 DB 에서 그대로 돌려 참조 식과 무작위 3,000건을 대조했다(다른 사례 0건).

<div class="table-wrap">

| 새로 찾은 차이                                             | 정한 것                                                  |
| ---------------------------------------------------- | ----------------------------------------------------- |
| 나누어떨어지는 배분에서 줄별로 10원이 다른 경우(합계는 같다)                  | 그대로 둔다 — 엔진은 정수로 정확한 비례값을 낸다                          |
| 부분 취소 때 쿠폰을 두 장 이상 쓴 줄의 쿠폰 몫이 클레임마다 1원 다른 경우(합계는 같다) | 그대로 둔다 — 엔진은 쿠폰마다 차감액을 알려 주려고 쿠폰별로 나눈다                |
| 수량과 상관없이 줄에 한 번 붙는 금액                                | 쇼핑몰이 따로 줄로 보낸다 — 엔진이 수량에 비례하지 않는 금액을 줄의 값으로 받게 하지 않는다 |

</div>

## 시험 연결 — 실제 주문 절차에 끼워 보기

버리는 로컬 DB 에 쇼핑몰의 DB 구조와 시험 데이터를 넣고, 쿠폰 · 포인트를 다루는 자리(미리보기 · 주문 생성 · 결제 확정 · 결재 반려와 결제 실패 · 결제 전 줄 취소 · 클레임)만 엔진 호출로 바꿨다. 주문은 쇼핑몰의 실제 주문 생성 절차가 만들고, 엔진이 계산한 금액이 쇼핑몰의 주문 · 클레임 기록에 그대로 들어간다.

<figure class="diagram"><img src="/content-assets/coupon/replay-and-trial/diagram-3.light.svg" alt="시험 연결 — 실제 주문 절차에 끼워 보기 다이어그램" class="diagram-light" loading="lazy" decoding="async"><img src="/content-assets/coupon/replay-and-trial/diagram-3.dark.svg" alt="시험 연결 — 실제 주문 절차에 끼워 보기 다이어그램" class="diagram-dark" loading="lazy" decoding="async"></figure>

- 주문 → 선점 → 확정 → 부분 반품 → 전체 취소, 결재 반려 · 결제 실패, 자동 해제 뒤의 늦은 확정이 끝까지 돌았다.
- 확정이나 클레임을 다시 보내도 포인트는 한 번만 빠지고 클레임은 한 번만 남았다.
- 자동 해제 뒤 확정은 쿠폰이 남아 있으면 다시 잡아 확정되고, 그사이 다른 주문이 쓴 쿠폰이면 거절됐다.
- 이번에 만든 주문 9건의 상태 · 쿠폰 합계 · 포인트 합계가 엔진의 주문 기록과 모두 맞았다(대사).

## 시험 연결에서 나온 것과 정한 것

<div class="table-wrap">

| 나온 것                                          | 정한 것                                                           |
| --------------------------------------------- | -------------------------------------------------------------- |
| 줄마다 포인트 종류별 환불액을 적는 쇼핑몰은 취소 앞뒤로 주문 기록을 읽어야 했다 | 취소 · 반품 응답의 줄에 포인트 종류별 환불액을 더했다 — 필드를 더한 것이라 이미 붙인 쇼핑몰을 깨지 않는다 |
| 부가세까지 포인트로 내는 주문                              | 받지 않는다 — 포인트는 줄 금액까지. 공개 API 와 계산 규칙을 바꾸지 않는다                  |
| 결재가 끝나면 쇼핑몰 서버가 쿠폰을 발행하고 싶다                   | 관리 화면에만 둔다 — 서비스 API 에 두면 API 키만으로 쿠폰을 발행할 수 있게 된다             |
| 수량과 상관없이 붙는 금액                                | 따로 줄로 보낸다 — 실제 주문으로 다시 확인했다                                    |

</div>

막힌 곳은 연동 가이드에 자주 묻는 질문 넷과 체크리스트 둘로 되돌려 적었다.

## 확인

- 재현 19사례는 계산 모듈 테스트에 들어 있어 DB 없이 늘 함께 돈다.
- 시험 연결은 DB 준비와 확인 스크립트로 다시 돌릴 수 있게 남겼다. 자동 확인 33개가 모두 예상대로였다(그 가운데 둘은 '엔진이 거절한다'가 예상).
- 시험 연결을 하는 동안 엔진 코드와 정한 규칙은 바꾸지 않았고, 엔진 쪽 결함은 나오지 않았다.
- 나눠 반품의 계산은 「나눠 반품할 때의 환불」, 동시 요청은 「선착순 발급과 원장 동시성」에 있다.
