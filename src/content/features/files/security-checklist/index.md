## 체크리스트를 테스트로

업로드 · 다운로드는 보안 점검에서 자주 지적되는 곳인데, 프로젝트마다 따로 구현해 보안 수준이 제각각이었다. 그래서 이 서버의 첫 버전 성공 기준을 <strong>'보안 체크리스트 모두 통과'</strong> 로 두었다. 그런데 문서로만 둔 체크리스트는 기능이 늘면 실제 동작과 어긋난다.\
체크리스트를 **위협 → 대응 → 테스트 방법** 세 칸 표로 쓰고, **행마다 통합 테스트 하나**가 표에 적힌 방법대로 확인하게 했다. 테스트 이름에는 행 번호와 위협을 그대로 붙였다. 기능을 더할 때는 설계 문서에 행을 먼저 넣고, 구현한 뒤 테스트를 붙였다.

## 업로드 검사 순서 — 싼 검사부터

서버를 거치는 업로드는 아래 순서로 거른다. 앞 단계에서 떨어질 파일은 뒤의 비싼 검사(악성코드 검사 · 이미지 처리)에 보내지 않는다.

<figure class="diagram"><img src="/content-assets/files/security-checklist/diagram-2.light.svg" alt="업로드 검사 순서 — 싼 검사부터 다이어그램" class="diagram-light" loading="lazy" decoding="async"><img src="/content-assets/files/security-checklist/diagram-2.dark.svg" alt="업로드 검사 순서 — 싼 검사부터 다이어그램" class="diagram-dark" loading="lazy" decoding="async"></figure>

- 형식 검사로는 정상 형식 안에 든 악성 기능(PDF 스크립트 · 매크로 · 압축 속 바이러스)을 막지 못해 악성코드 검사를 둔다. 검사기에는 줄이거나 바꾸기 전, **올린 원본 그대로**를 보낸다.
- 검사기가 멈추면 받고 '검사 못 함'으로 남긴다(가용성 우선). 검사기가 돌아오면 그 파일만 다시 검사하고, 악성이면 시스템이 휴지통으로 옮긴다.
- 사진 원본은 위치(GPS)만 지우고, 썸네일에는 메타데이터를 남기지 않는다.

## 행을 쓰다 찾은 구멍

<aside class="callout tone-blue" data-icon="🔍">

**이중 방어로 건 DB 제약이 사유 없는 휴지통 기록을 받았다**\
관리자 휴지통은 API 가 사유를 검사하고, DB 에도 '휴지통이면 사유와 메모가 반드시 있다'는 CHECK 제약을 걸었다. 그런데 사유 칸이 비면(NULL) 비교 결과도 NULL 이 되고, CHECK 는 결과가 거짓일 때만 막으므로 사유 없는 행이 통과했다. 같은 날 다음 마이그레이션에서 IS NOT NULL 을 더해 다시 걸고, 사유가 비거나 없는 값인 행이 거부되는 테스트를 더했다.

</aside>
