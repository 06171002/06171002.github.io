## 서버를 거치지 않는 업로드

지금까지의 업로드는 브라우저 → 서비스 서버 → 파일 서버 → 저장소 순서로, 파일 바이트가 **서버를 두 번** 지났다. 대량 등록 때는 대역폭 · 메모리 · 시간 제한이 병목이 된다. 직접 업로드는 **브라우저가 저장소에 바로 올리고**, 서버들은 주소 발급과 확인만 한다.

<figure class="diagram"><img src="/content-assets/files/direct-upload/diagram-1.light.svg" alt="서버를 거치지 않는 업로드 다이어그램" class="diagram-light" loading="lazy" decoding="async"><img src="/content-assets/files/direct-upload/diagram-1.dark.svg" alt="서버를 거치지 않는 업로드 다이어그램" class="diagram-dark" loading="lazy" decoding="async"></figure>

- ① ③ ⑤ 는 서비스 서버가 부른다. API 키는 서비스 서버에만 있고, 브라우저는 파일 서버를 부르지 않는다.
- 직접 업로드를 쓰지 않는 서비스는 바꿀 것이 없다. 기존 업로드 방식과 파일 상태는 그대로다.

## 검사 전 파일은 따로 둔다

브라우저가 저장소에 바로 올리면 **서버가 검사하기 전의 파일**이 생긴다. 이름만 바꾼 실행 파일이나 악성코드가 검사 전에 쓰이면 안 된다. 그래서 처리 전 업로드는 **파일과 다른 기록**으로 두고, 처리를 통과해야 파일 기록이 생긴다.

<div class="table-wrap">

| 정해야 했던 것        | 고른 것                                             | 고르지 않은 것과 이유                                                                                           |
| --------------- | ------------------------------------------------ | ------------------------------------------------------------------------------------------------------ |
| 처리 전 상태를 둘 곳    | 파일과 따로 둔 처리 전 업로드 기록                             | 파일 기록에 상태를 더하기 — 파일 기록은 해시 · 크기 · 저장 경로가 반드시 있는 '검사를 통과한 파일'을 전제로 한다. 필수 값을 풀어야 하고 모든 조회가 새 상태를 걸러야 한다 |
| 받은 파일을 둘 곳      | 검사 전 경로에 받고, 통과하면 정식 경로에 다시 쓴다                   | 정식 경로에 바로 받고 상태로만 막기 — 같은 주소로 다시 올리면 검사를 통과한 파일이 바뀔 수 있다                                               |
| 업로드 주소가 묶는 것    | 경로 · 크기 · 형식을 서명에 묶은 주소                          | 크기 범위만 거는 업로드 정책 — 경로와 형식, 정확한 크기를 묶지 못한다                                                              |
| 처리 중에 확정하면      | 항목별로 '아직 준비 안 됨' — 서비스가 잠시 뒤 다시 확정               | 확정을 받아 두고 처리가 끝나면 확정 — 실패를 서비스에 따로 알려야 한다                                                              |
| 악성코드 검사기를 못 쓸 때 | 짧게 다시 시도한 뒤 '검사 못 함'으로 받고, 검사기가 돌아오면 그 파일만 다시 검사 | 검사기가 돌아올 때까지 처리 중으로 두기 — 그동안 확정할 수 없다                                                                  |

</div>

## 완료 알림 때 먼저 거른다

전체 파일을 읽는 일은 작업자에게 넘기고, 완료 알림에서는 저장소에서 **크기와 앞부분만** 읽어 싼 검사부터 한다.

<figure class="diagram"><img src="/content-assets/files/direct-upload/diagram-3.light.svg" alt="완료 알림 때 먼저 거른다 다이어그램" class="diagram-light" loading="lazy" decoding="async"><img src="/content-assets/files/direct-upload/diagram-3.dark.svg" alt="완료 알림 때 먼저 거른다 다이어그램" class="diagram-dark" loading="lazy" decoding="async"></figure>

- 앞부분은 **최대 1MB** 를 범위 요청으로 읽는다. 형식은 앞부분만으로 판별된다.
- JPEG 의 가로 · 세로는 그림 앞의 부가 정보 구간(APP 세그먼트)이 1MB 안이면 읽히고, 넘으면 '모름'으로 두어 작업자가 전체 파일로 다시 본다. 실험: 부가 정보 0 · 200 · 900KB → 640×480 을 읽음, 1,100KB · 3MB → 모름, 전체를 읽으면 모두 640×480.
- 완료 알림은 여러 번 불러도 안전하다. 같은 답을 주고 작업은 하나만 생긴다.

## 확인

로컬 시험 저장소는 **서명을 검사하지 않았다** — 크기 · 형식이 다른 요청, 경로나 서명을 고친 요청, 만료된 주소를 모두 받아 저장했다. 그래서 서명 범위는 발급한 주소의 단위 테스트로, 크기 · 형식 방어는 완료 검사의 통합 테스트로 확인하고, 둘 다 보안 체크리스트의 행으로 남겼다. 저장소가 막는지는 **시범 연동의 실제 저장소**에서 확인했다.

| 실제 저장소에 보낸 요청      | 결과  |
| ------------------ | --- |
| 서명을 한 글자 고친 주소     | 403 |
| 경로(파일 ID)를 바꾼 주소   | 403 |
| 서명과 다른 형식으로 보냄     | 403 |
| 알린 크기보다 크거나 작은 본문  | 403 |
| 만료(시험용으로 2분) 뒤에 올림 | 403 |

</div>

- 악성코드 검사기를 멈춘 채 올린 파일은 짧게 다시 시도한 뒤 '검사 못 함'으로 받았고, 검사기를 다시 켜자 **43초 뒤** 재검사에서 '깨끗함'으로 바뀌었다.
- 기존 사내 서비스의 업로드 흐름(발급 → 브라우저가 올림 → 확인)과 화면은 거의 그대로 두고 바꿀 수 있었다.
