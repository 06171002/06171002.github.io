## 개요

업로드된 오디오 파일을 **백그라운드(Celery)로 전사·요약**하고, 진행 상황을 **SSE로 실시간 푸시**하는 파이프라인. `파일 업로드(202) → Celery 큐 → STT 세그먼트 스트리밍 → LLM 구조화 요약 → DB 저장` 으로 동작하며, 클라이언트는 SSE로 *과거 세그먼트 → 실시간 진행 → 최종 요약* 을 순서대로 받는다.

<div class="table-wrap">

| **비동기 접수** | **Celery 동시성 4** | **SSE 3단계** | **Look-ahead** | **3단계 에러 후처리** |
| ---------- | ---------------- | ----------- | -------------- | -------------- |
| 202 즉시 응답  | 재시도 지원           | 과거+실시간+요약   | 메모리 효율 스트리밍    | DB 로그·상태·통보    |

</div>

---

## 왜 이 설계가 필요했는가 (Problem)

<aside class="callout tone-scenario" data-icon="⏳">

**시나리오 1 — 동기 처리 시 타임아웃**\
긴 오디오의 전사+요약은 수십 초\~수 분이 걸린다.\
→ HTTP 요청 안에서 동기로 처리하면 **게이트웨이 타임아웃·커넥션 점유**가 발생한다.

</aside>

<aside class="callout tone-scenario" data-icon="🕳️">

**시나리오 2 — 완료까지 깜깜이**\
STT가 전부 끝나야 결과를 주면, 사용자는 그동안 진행 상황을 전혀 알 수 없다.\
→ 긴 녹음일수록 **체감 대기**가 길다.

</aside>

<aside class="callout tone-scenario" data-icon="🔌">

**시나리오 3 — 중간 연결도 진행 파악 필요**\
클라이언트가 작업 도중에 SSE를 연결하면, 이미 발행된 과거 세그먼트를 놓쳐 화면이 비어 보인다.

</aside>

## 핵심 설계 결정

### 1. Look-ahead 세그먼트 스트리밍

<aside class="callout tone-orange" data-icon="🔭">

다음 세그먼트를 미리 한 칸 읽어 **현재가 마지막인지 판별**한다.

- **중간 세그먼트** — '처리 중' 태깅
- **마지막 세그먼트** — '전사 완료' 태깅
- 각 세그먼트를 **즉시 DB 저장 + Redis 발행** — 한 개씩만 메모리에 유지

</aside>

```text
# look-ahead 로 마지막 세그먼트 식별
현재 = next(전사 제너레이터)
while True:
    try:
        다음 = next(전사 제너레이터)  # 다음을 미리 읽음
        저장 후 발행(현재, 상태=처리 중)
        현재 = 다음
    except StopIteration:  # 다음이 없으면 = 마지막
        저장 후 발행(현재, 상태=전사 완료)
        break
```

### 2. SSE 3단계 (과거 replay + 실시간 구독)

<aside class="callout tone-blue" data-icon="📡">

① DB의 **과거 세그먼트를 replay**(과거 표시)\
② 이미 완료면 최종 요약을 즉시 전송 후 종료\
③ 진행 중이면 **Redis Pub/Sub 구독**\
→ 늦게 연결해도 **전체 히스토리**를 받고, 완료된 작업은 불필요한 구독을 하지 않는다.

</aside>

```text
# SSE 이벤트 생성기
for 세그먼트 in DB 의 과거 세그먼트:  # ① 과거 replay
    yield SSE(세그먼트, 과거=True)
if 작업 상태 == 완료:  # ② 이미 완료 → 즉시 종료
    yield SSE(최종 요약); return
async for 메시지 in Redis 구독(작업 ID):  # ③ 실시간 구독
    yield SSE(메시지)
    if 메시지 종류 in (최종 요약, 오류): break
```

### 3. 3단계 에러 후처리 (컨텍스트 매니저)

<aside class="callout tone-green" data-icon="🛡️">

async 컨텍스트 매니저로 파이프라인 예외를 **한 곳에서** 잡는다. 구조화 로그를 남긴 뒤 3단계로 후처리한다.\
① **에러 로그 테이블** 적재 (단계 · 메시지 · 스택)\
② 상태를 **실패**로 갱신\
③ **Redis로 에러 이벤트 발행** — SSE 클라이언트 즉시 통보

</aside>

```text
# 에러 컨텍스트 — 파이프라인 예외를 한 곳에서 처리
로그.error("[단계] 처리 중 오류", 작업 ID, exc_info=True)  # 구조화 로그
await 에러 로그 기록(작업 ID, 단계, 메시지 + 스택)  # ① DB
await 상태 갱신(작업 ID, 실패, 메시지)  # ② 상태
이벤트 발행(작업 ID, {종류: 오류, 메시지})  # ③ 통보
```

## 설계가 만든 결과 (Result)

<aside class="callout tone-blue" data-icon="📊">

핵심 설계 1(**Look-ahead 세그먼트 스트리밍**)을 테스트로 검증했다.\
SSE 클라이언트는 이 태그로 **스트림 종료 시점을 판단**하므로, 태그가 어긋나면 화면이 영원히 기다리거나 대화가 잘린 채 끝난 것처럼 보인다.

</aside>

### 검증 결과

look-ahead 파이프라인 테스트 · **10/10 통과**

<div class="table-wrap">

| **구분**                | **검증 내용**                                                                 |
| --------------------- | ------------------------------------------------------------------------- |
| <strong>★ 태깅</strong> | 세그먼트가 몇 개든 <strong>마지막 하나만 '전사 완료'</strong>, 나머지는 '처리 중' (1\~30개 랜덤)      |
| 경계                    | 세그먼트가 <strong>하나뿐이면 그 하나가 바로 '전사 완료'</strong> — off-by-one 이 가장 잘 드러나는 지점 |
| 순서                    | 세그먼트 번호 1부터 순차 · 본문과 DB 저장 순서 일치                                          |
| 누락방지                  | 각 세그먼트마다 **저장과 발행이 모두** 수행                                                |
| 흐름                    | 전사 후 '전사 완료' → LLM 요약 → 최종 요약 발행 → '완료'                                   |
| 무음                    | 세그먼트 0개면 **LLM 미호출 + '완료'로 종결**, 오류 이벤트 없음                                |
| 실패                    | 전사 도중 예외 → 오류 이벤트 발행 + DB 로그, **예외는 삼켜 Celery 태스크가 안 죽는다**                |

</div>

<aside class="callout tone-green" data-icon="✅">

look-ahead 는 **off-by-one 이 나기 가장 쉬운 패턴**이라 세그먼트 개수를 1\~30 으로 랜덤하게 바꿔가며 **정확히 하나만** '전사 완료'인지 확인했다.\
특히 세그먼트가 1개인 경우(첫 세그먼트 = 마지막)는 로직상 분기가 달라 별도 경계 테스트로 고정했다.

</aside>

### 무음을 실패로 처리하지 않는 것도 계약이다

<aside class="callout tone-gray" data-icon="🔇">

세그먼트가 하나도 없으면(무음 파일·인식 불가) **실패가 아니라 빈 요약으로 정상 종결**한다.

- LLM 을 호출하지 않는다 — 빈 대화록으로 호출하면 비용만 나간다
- 오류 이벤트를 발행하지 않는다 — 발행하면 SSE 클라이언트가 실패로 표시한다

둘 다 테스트로 잠갔다.

</aside>

### 이 검증이 말하지 않는 것

<aside class="callout tone-gray" data-icon="📐">

- **SSE 3단계 구독은 미검증** — 과거 replay → 완료 즉시종료 → 실시간 구독 분기는 엔드포인트 계층이라 별도다. 본 테스트는 **발행 측**만 확인했고 Redis Pub/Sub → 구독 도달은 포함되지 않았다.
- **메모리 효율은 미측정** — "한 개씩만 메모리에 유지"는 구현 의도이지 측정된 값이 아니다.
- **Celery 재시도·동시성은 미검증** — 실제 워커 환경이 필요하다.

</aside>

## 배포 환경에서의 자원 예산 (2026-08-30 확인)

<aside class="callout tone-orange" data-icon="⚖️">

배치 워커와 실시간 스트리밍 API 는 **같은 서버의 같은 CPU 를 나눠 쓴다** (GPU 없음).

그래서 이 카드의 「Celery 동시성 4」는 독립된 숫자가 아니라 **실시간 경로와의 예산 분할** 결과다.

</aside>

<div class="table-wrap">

| **서비스** | **역할**       | **스레드 설정**              | **최대 점유**       |
| ------- | ------------ | ----------------------- | --------------- |
| API 서버  | 실시간 스트리밍     | 추론 스레드 6                | 세션 수 × 워커 3 × 6 |
| 워커      | **배치 전사·요약** | 추론 스레드 2 · Celery 동시성 4 | 자식 4 × 2스레드 ≈ 8 |

</div>

<aside class="callout tone-gray" data-icon="🧭">

배포 설정의 주석이 의도를 남기고 있다 — <em>「실시간 스트리밍은 API 프로세스가 전담하고 워커는 배치 작업만 처리하므로 API 에 코어를 더 배분」</em>, 그리고 <em>「동시성 2 + 추론 스레드 제한으로 코어 과다점유 방지」</em>.

다만 주석의 동시성 2 와 달리 실제 설정은 4 다. 그래도 배치 쪽은 **최대 8 스레드로 상한이 있고**, 상한이 없는 쪽은 실시간 경로다(세션마다 스레드풀이 새로 생김 — 「실시간 스트리밍 STT」 카드 참조).

</aside>

### 배치와 실시간은 STT 설정이 갈린다

<div class="table-wrap">

| **설정**  | <strong>실시간(API 서버)</strong> | <strong>배치(워커)</strong> | **이유**                                                                |
| ------- | ---------------------------- | ----------------------- | --------------------------------------------------------------------- |
| beam 크기 | 1 (greedy)                   | **5**                   | 배치는 지연 제약이 없어 정확도를 택할 수 있다. 주석: <em>「그리디(1)는 "가정"→"과정" 류 오인식 발생」</em> |
| 연산 정밀도  | int8                         | int8                    | <em>「int8_float32 는 출력이 문자단위로 동일하고 속도도 같아 무의미」</em>                   |

</div>

> **같은 엔진 추상화 위에서 경로별로 다른 트레이드오프를 고른 사례**다 — 실시간은 지연을, 배치는 정확도를 우선한다. 「멀티 엔진 추상화」 카드의 설계가 실제로 값을 하는 지점이기도 하다.

<aside class="callout tone-gray" data-icon="📐">

**이 절이 말하지 않는 것**

- 🔴 **배치 경로의 성능은 측정하지 않았다** — 2026-08-30 실측은 **실시간 스트리밍만** 다뤘다. 파일 길이 대비 전사·요약 소요, Celery 큐 대기, 동시 배치 작업 수용량은 전부 미측정이다.
- **실시간·배치 동시 부하도 미측정** — 두 경로가 같은 CPU 를 다툴 때 서로를 얼마나 굶기는지는 재지 않았다. 위 예산 분할이 실제로 충분한지는 그 측정 뒤에야 말할 수 있다.
- 본문의 look-ahead·무음·실패 처리 검증(10/10)은 **로직 계약**이며 성능과는 별개다.

</aside>
