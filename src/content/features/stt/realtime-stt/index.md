## 개요

WebSocket으로 들어오는 오디오 청크를 **버퍼링 없이 실시간 전사**하는 파이프라인. `수신(WS) → 포맷 변환 → Silero VAD 발화 분할 → STT 워커 큐 → 결과 큐 → Redis 브로드캐스트 / DB 저장` 의 비동기 흐름으로 동작하며, 무거운 STT 추론이 async 이벤트 루프를 막지 않도록 **ThreadPoolExecutor로 오프로딩**했다.

<div class="table-wrap">

| **WebSocket 양방향** | **STT 워커 3**       | **Silero VAD**    | **2단 큐**   | **종료 플러시** |
| ----------------- | ------------------ | ----------------- | ---------- | ---------- |
| 청크 수신 + 결과 송신     | ThreadPoolExecutor | 16kHz·32ms·임계 0.5 | 입력 / 결과 분리 | 잔여 버퍼 패딩   |

</div>

---

## 왜 이 설계가 필요했는가 (Problem)

<aside class="callout tone-scenario" data-icon="🎯">

**시나리오 1 — 이벤트 루프 블로킹**\
STT 추론은 CPU/GPU 동기 연산이다. async 이벤트 루프에서 직접 호출하면 추론하는 동안 다른 WebSocket의 수신·송신이 모두 멈춰 실시간성이 깨진다.

</aside>

<aside class="callout tone-scenario" data-icon="🔇">

**시나리오 2 — 무음 구간까지 STT 호출**\
들어오는 모든 오디오를 STT에 넣으면 침묵 구간도 연산해 자원을 낭비하고, 무음에서 환각(hallucination) 텍스트가 생성된다.

</aside>

<aside class="callout tone-scenario" data-icon="📤">

**시나리오 3 — 연결 종료 시 마지막 발화 유실**\
VAD가 발화 종료를 확정하기 전에 WebSocket이 끊기면, 버퍼에 남은 마지막 발화가 전사되지 않고 사라진다.

</aside>

## 핵심 설계 결정

### 1. 입력/결과 큐 분리 + ThreadPoolExecutor 오프로딩

<aside class="callout tone-orange" data-icon="⚡">

수신과 인식을 디커플링하기 위해 **입력 큐·결과 큐를 분리**하고, STT 추론은 `run_in_executor`로 스레드풀(워커 3개)에 넘겨 이벤트 루프를 비운다.

</aside>

```text
# STT 워커 — 입력 큐에서 꺼내 스레드풀에서 추론
세그먼트 = await 입력 큐.get()
텍스트 = await 이벤트 루프.run_in_executor(
    스레드풀,  # ThreadPoolExecutor · 워커 3개
    세그먼트 전사,  # Whisper 추론 (블로킹)
    세그먼트, 직전 문맥 프롬프트,
)
await 결과 큐.put({텍스트, 세그먼트 번호, 시각})
```

### 2. Silero VAD 상태머신 발화 분할

<aside class="callout tone-blue" data-icon="🎧">

16kHz·32ms 프레임마다 Silero VAD로 음성 확률을 구하고, 상태머신으로 세그먼트를 자른다.

- **발화 시작** — 연속 음성 5프레임(160ms) 이상
- **발화 종료** — 침묵 20프레임(640ms)

→ 무음 구간은 **STT 호출에서 제외**된다.

</aside>

```text
# 프레임마다 음성 확률 판정 → 발화가 끝나면 세그먼트 반환
음성 확률 = VAD 모델(프레임, 16kHz)
if 음성 확률 >= 임계값:  # 0.5
    발화 버퍼에 프레임 추가; 음성 프레임 수 += 1
elif 발화 중 and 침묵 프레임 수 >= 최대 침묵:  # 20프레임
    return 발화 버퍼 전체  # 발화 종료 → 세그먼트 반환
```

### 3. 포맷별 디코딩 전략

<aside class="callout tone-blue" data-icon="🧩">

실시간 청크는 코덱마다 디코딩 방식이 달라 **포맷별 전략을 분기**한다.

- **Raw PCM** — NumPy 직처리(최속)
- **Opus/WebM** — PyAV Parser 스트리밍
- **그 외** — Pydub 폴백

</aside>

```text
# 디코딩 전략 선택
if 입력 포맷 in [PCM, raw]: return NumPy 직처리
if 입력 포맷 in [Opus, WebM] and 스트리밍 포맷: return PyAV 파서
return Pydub  # MP3 등 폴백
```

### 4. 연결 종료 시 버퍼 플러시

<aside class="callout tone-green" data-icon="📤">

연결이 끊기면(`WebSocketDisconnect`),\
① 변환기의 잔여 버퍼를 flush\
② 한 프레임에 못 미치면 **0 패딩으로 채워 강제 전사**\
③ STT 워커 완료를 대기\
→ <strong>마지막 발화 유실을 막는다.</strong>

</aside>

```text
# 연결 종료 처리
남은 오디오 = 변환기.flush()
if 남은 오디오 and 길이 < 프레임 크기:
    남은 오디오 += 0 바이트 × (프레임 크기 - 길이)  # 패딩
파이프라인에 남은 오디오 투입  # 강제 전사
최종 결과 = await STT 워커 완료 대기
```

## 설계가 만든 결과 (Result)

<aside class="callout tone-blue" data-icon="📊">

이 설계의 핵심 주장은 <strong>"무음 구간은 STT 호출에서 제외된다"</strong> 다. 자원 낭비와 환각(hallucination)을 동시에 막는 근거이므로, **상태머신 테스트로 검증**했다.

</aside>

### 검증 결과

발화 분할 상태머신 테스트 · **17/17 통과** (pytest + hypothesis)

<div class="table-wrap">

| **검증 내용**                                   | **방식**                     |
| ------------------------------------------- | -------------------------- |
| **무음만 들어오면 세그먼트가 한 번도 나오지 않는다**             | hypothesis 300 케이스 (임의 길이) |
| **최소 발화길이(5프레임) 미달은 침묵이 와도 버려진다**           | hypothesis 200 케이스         |
| 연속 음성 5프레임에 도달해야 발화로 인정된다                   | 경계                         |
| 침묵 20프레임 도달 시 세그먼트 반환 · **19프레임까지는 반환 안 함** | 경계 양방향                     |
| 세그먼트 반환 후 상태 완전 초기화 (모델 내부 상태 포함)           | —                          |
| **프레임 크기가 다르면 무시하고 상태를 바꾸지 않는다**            | 5가지 크기                     |
| 종료 플러시는 최소길이 조건을 무시하고 남은 버퍼를 반환한다           | 종료 유실 방지                   |
| 민감도 설정 3 이상 → 임계값 0.6 상향                    | 설정 변환                      |

</div>

<aside class="callout tone-green" data-icon="✅">

앞의 두 불변식이 <strong>§2 Silero VAD 상태머신의 존재 이유</strong>를 직접 뒷받침한다 — 침묵과 짧은 잡음은 STT 로 흘러가지 않는다.\
프레임 크기 검증 테스트는 부분 청크가 상태머신을 오염시켜 **발화 경계가 어긋나는 상황**을 막는다.

</aside>

### 모델은 스텁, 상태머신은 실물로 테스트했다

<aside class="callout tone-evidence" data-icon="🧪">

Silero 모델의 **정확도는 그 프로젝트의 책임**이고, 내가 만든 것은 **확률값을 받아 발화 경계를 자르는 상태머신**이다.\
그래서 모델을 "프레임별 음성 확률을 테스트가 지정하는" 스텁으로 대체해 경계 조건을 **결정론적으로** 고정했다. 실제 모델을 로드하면 수백 MB 다운로드에 확률도 비결정적이라 경계를 검증할 수 없다.\
단, **설정 상수는 하드코딩하지 않고** 실제 설정 파일을 경로 로드해 쓴다 — 운영 값이 바뀌면 테스트가 반응해야 하기 때문이다.

</aside>

### 테스트를 짜다 드러난 구조 문제

<aside class="callout tone-red" data-icon="⚠️">

VAD 하나를 검증하려는데 <strong>임포트가 안 됐다.</strong>

서비스 패키지의 초기화 모듈이 하위 모듈 전부를 **eager import** 하고, 그 연쇄로 Gemini SDK·Celery·OpenAI 클라이언트가 전부 로드된 뒤 **임포트 시점에 Redis 로 실제 커넥션을 시도**하다가 실패한다.

→ 현 구조에서는 **인프라 없이 순수 로직만 검증하는 것이 불가능**하다. 대상 모듈만 파일 경로로 단독 로드하는 테스트 설정으로 우회했으나, 이건 **해결이 아니라 회피**다.\
서비스 패키지가 lazy import 를 쓰거나 클라이언트 생성을 함수 안으로 미루면 이 우회는 필요 없어진다.

</aside>

> 부수적으로 의존성 목록에 **Gemini SDK 패키지가 누락**된 것도 확인했다 (코드는 그 SDK 를 임포트한다). 도커 이미지에서만 우연히 해결되고 있었다.

### 이 검증이 말하지 않는 것

<aside class="callout tone-gray" data-icon="📐">

- **자막 지연·수용량은 2026-08-30 실측했다** (아래 「배포 환경 실측」 절). 다만 **지연의 75%는 여전히 구간을 특정하지 못했다** — 큐·스레드풀·버퍼링을 구분할 로그 마커가 없기 때문이다.
- **VAD 정확도는 검증 대상이 아니다** — "사람 목소리를 잘 감지하는가"는 Silero 모델의 성능이고, 본 테스트는 그 출력을 **어떻게 경계로 바꾸는가**만 다룬다.
- **지연 분포는 미측정** — 세션당 p50/p95 는 수집하지 않았다. 아래 실측은 세그먼트 4개의 개별값이다.
- **종료 플러시의 호출 경로는 미검증** — 플러시 자체는 테스트했지만, WebSocket 종료 시 0 패딩 후 강제 전사하는 엔드포인트 흐름은 포함되지 않았다.

</aside>

## 배포 환경 실측 (2026-08-30)

<aside class="callout tone-blue" data-icon="📡">

**로컬이 아니라 실제 배포 서버에서 쟀다** — **GPU 없이** CPU 로만 추론하는 이미지다.\
30초 한국어 음성을 <strong>실시간 배속(1.0x)</strong> 으로 WebSocket에 흘리고, 발화가 끝난 시점부터 **전사 결과가 DB 에 기록된 시각**까지를 자막 지연으로 판정했다.

</aside>

### 동시 4세션 — 실시간 자막이 죽는다

<div class="table-wrap">

| **지표**           | **단일 세션** | **동시 4세션**                |
| ---------------- | --------- | ------------------------- |
| **스트리밍 중 수신 자막** | 2건        | 🔴 **0건**                 |
| 세션당 세그먼트         | 4개        | 2개 (VAD 분할이 바뀜)           |
| 세션 소요            | 37.5초     | 55.5초                     |
| 마지막 전사 기록        | 스트림 내     | 🔴 **클라이언트 종료 후 17\~20초** |

</div>

<aside class="callout tone-red" data-icon="🔥">

<strong>4세션에서 실시간성이 완전히 무너진다.</strong> 스트리밍 중에는 자막이 한 건도 도착하지 않고, 전사는 클라이언트가 끊긴 뒤까지 이어진다.\
→ 이 서버의 실시간 수용량은 **4세션 미만**이다.

</aside>

<aside class="callout tone-orange" data-icon="🔍">

**구조적 원인 후보 — 세션마다 스레드풀이 따로 생긴다**\
스트리밍 엔드포인트가 **세션마다** 워커 3개짜리 파이프라인을 만들고, 컨테이너의 추론 스레드 수(OpenMP)는 6 이다.\
→ 4세션이면 **3 × 4 × 6 = 최대 72 스레드가 코어 수를 크게 넘겨** 경합한다(오버서브스크립션).

⚠️ 덧붙여 설정 파일의 스트림 워커 수(3)는 **읽히지 않는다** — 엔드포인트가 값을 하드코딩해서 설정을 바꿔도 반영되지 않는다.

</aside>

### 원인 가설을 세우고 — 측정으로 기각했다

<aside class="callout tone-evidence" data-icon="🧪">

**가설** — 세션마다 스레드풀이 따로 생기므로(워커 3 × 추론 스레드 6) 4세션이면 최대 72 스레드가 코어를 두고 경합해 무너진다. <strong>그렇다면 스레드를 줄이면 완화돼야 한다.</strong>

추론 스레드 수(OpenMP · STT 엔진 양쪽)를 **6 → 2** 로 낮추고 같은 실험을 반복했다.

</aside>

<div class="table-wrap">

| **지표**           | **threads=6** | **threads=2**                  |
| ---------------- | ------------- | ------------------------------ |
| 단일 세션 자막 지연      | 5.2s          | 🔴 **9.2 → 11.1s** (세그먼트마다 누적) |
| 단일 세션 소요         | 37.5s         | 47.6s                          |
| **4세션 스트리밍중 자막** | 0건            | <strong>0건 (변화 없음)</strong>    |
| 4세션 소요           | 55.5s         | 55.6s                          |

</div>

<aside class="callout tone-red" data-icon="❌">

<strong>가설 기각.</strong> 스레드를 3분의 1로 줄여도 4세션 붕괴는 **전혀 달라지지 않았고**, 단일 세션만 2배 나빠졌다. 경합이 원인이었다면 개선이 나왔어야 한다.

오히려 배포 설정에 남아 있던 <em>「4→6: 결과 지연이 세그먼트마다 누적되던 문제 대응」</em> 이라는 주석이 **내 측정으로 역검증**됐다 — 2로 낮추자 그 누적 패턴이 그대로 재현됐다.

</aside>

<aside class="callout tone-blue" data-icon="🧭">

**그래서 정확한 서술은 이것이다**\
단일 세션 지연을 줄이려면 스레드가 **많아야** 하고, 다중 세션을 버티려면 **적어야** 한다 — 고 생각했으나 <strong>후자는 사실이 아니었다.</strong> 스레드 축으로는 4세션 문제를 건드릴 수 없다.\
→ 원인은 **미규명**이다. 모델 코드에 명시적 락·세마포어는 없으므로 후보는 faster-whisper 내부 직렬화 · 단일 uvicorn 프로세스의 이벤트 루프 경합 · 종료 시 워커 완료 대기 경로 정도이나, <strong>근거 없이 단정하지 않는다.</strong>

</aside>

<aside class="callout tone-gray" data-icon="📐">

**이 실측이 말하지 않는 것**

- 🔴 **부하 중 CPU 를 재지 않았다** — load average 2.50 은 부하 **종료 후** 값이고 1분 감쇠 평균이라 피크가 아니다. 따라서 위 오버서브스크립션은 <strong>구조적 근거는 있으나 실측으로 확정되지 않았다.</strong> "CPU 병목이 아니다"라고 말할 수 없다.
- **지연의 75% 구간을 특정하지 못했다** — 큐 대기·스레드풀 스케줄링·프레임 버퍼링을 구분할 로그 마커가 없다. 마커를 넣는 것이 다음 과제다.
- **DB 기록 시각은 초 단위** — 5.5초 측정에 ±1초 오차가 붙는다.
- **표본은 30초 오디오 1종** — 화재예방 안내 방송이며 **실제 서비스 도메인의 음성이 아니다**. 세션 수도 1과 4 두 점뿐이라 한계 지점을 좁히지 못했다.

</aside>
